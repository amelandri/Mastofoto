# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Mastofoto is a static, single-user web app (`index.html` + `style.css` + `app.js`, plus `pure.mjs` for a handful of DOM-free functions) that lets someone log into a Mastodon instance, pick one Mastodon list (or their Home timeline), and view only the posts there that contain photos (image attachments), with the ability to favourite and reblog them. It runs entirely client-side against the Mastodon REST API — there is no backend, no build step, and no database. All persisted state lives in the browser's `localStorage`. The page has no runtime dependencies besides the Mastodon instance itself; the header wordmark is a pre-rendered static image (`assets/logo.png`) rather than a webfont, so nothing is fetched from a font CDN at runtime. All UI copy (labels, buttons, error messages) is in English (`<html lang="en">`) — the app was originally built with Italian strings, fully translated later, so don't reintroduce Italian text when adding new user-facing strings.

## Development

There is no build step and no runtime dependencies. `package.json` exists solely to declare `"type": "module"` (so `app.js`'s `import` from `pure.mjs` resolves the same way for Node — `node --check`/`node --test` — as it does in the browser via `<script type="module">`); it has no dependencies and nothing to `npm install`.

- Opening `index.html` directly as a `file://` page does **not** work for testing login — the OAuth redirect flow needs a real `http(s)://` origin (see Architecture below), and browsers also block ES module imports (`<script type="module">`) from `file://` regardless. Serve the directory instead, e.g. `python3 -m http.server`, and use `http://localhost:8000/`.
- **Don't use VS Code's "Live Preview" extension** to test this app in an external browser: it gates its static files behind an internal auth cookie/token that's only present when the page is opened *through VS Code itself*. Loading the same `http://localhost:3000/...` URL directly in a real browser tab gets `app.js` a `401 Unauthorized` (silently breaking everything, since no JS ever runs — this looks like "login doesn't work" but is really "nothing runs"), and its injected live-reload script tries to open a `ws://` connection that this app's CSP correctly blocks (`connect-src https:` — harmless, just means Live Preview's auto-refresh won't work, not a real problem). Plain `python3 -m http.server` has neither issue.
- After editing `app.js` or `pure.mjs`, check they parse with `node --check <file>`.
- Run the test suite with `node --test` (or `npm test`) — it covers the pure functions in `pure.mjs` (`isHttpUrl`, `hasPhoto`, `parseNextMaxId`) via `pure.test.mjs`, using Node's built-in test runner, no added dependency. `sanitizeStatusHtml()` in `app.js` is **not** covered here — it needs `DOMParser`, which Node doesn't provide without adding a dependency (e.g. jsdom), so it stays manually reviewed rather than unit-tested. When touching `pure.mjs`, keep behavior identical between the browser and Node call paths — see `isHttpUrl`'s `base` parameter below.
- End-to-end testing (OAuth login, list fetching, favourite/reblog) requires a real Mastodon account/instance and cannot be simulated locally.
- Testing from a real phone against the dev server means browsing to the Mac's LAN IP (e.g. `http://192.168.0.15:8000`) instead of `localhost` — that origin is **not** a secure context (only HTTPS and `http://localhost`/`127.0.0.1` count), so any Web Crypto API gated behind one becomes unavailable there even though the exact same code works from `http://localhost:8000`. Login's `state` generation already tolerates this (see the `randomUUID()` helper in Architecture below). `navigator.serviceWorker.register()` has the same secure-context requirement and is *not* worked around the same way — its existing `.catch(() => {})` just means it silently no-ops on a plain LAN IP instead of erroring, which is fine since offline caching is a nice-to-have, not something login depends on.

**Branches:** there are three. `dev` is where new work happens (in-progress features/fixes land here first, not directly on `main`). `main` is the clean, open-source branch (what this repo looks like to the world / forks) — merge `dev` into it once work is settled. `production` is what GitHub Pages actually serves; it's `main` plus a small personal layer (a `rel="me"` link back to the site owner's Mastodon profile, an Umami analytics script tag, and a one-line disclosure on the login page — right after `.app-disclosure`, styled with the plain `.hint` class rather than `.app-disclosure` itself so it doesn't add a second divider — mentioning that this specific deployment runs that analytics) that must never be merged back into `main` or `dev`. The flow is `dev` → `main` → `production`, each step a manual merge when ready — nothing here is automatic or CI-driven:
```
git checkout main && git merge dev && git push origin main
git checkout production && git merge main && git push origin production
```
The personal-layer commits on `production` stay on top and shouldn't conflict since they only touch a couple of lines in `index.html`'s `<head>` and its CSP `script-src`.

**Releasing a version:** every release (whenever the user asks to "release version X.Y.Z") must, in addition to the usual changelog-entry-plus-git-tag flow: (1) update the `APP_VERSION` constant near the top of `app.js` to the new version, which is what's displayed on the "About Mastofoto" page (`#app-version`, set once at startup) — do this even for a patch release with no other user-visible change, since the version display existing at all is the point.

## Architecture

All logic lives in `app.js` as a single IIFE with a small `state` object (`instance`, `token`, `accountId`, `currentListId`) and an `el` object caching DOM references. Views are plain `<section>`s in `index.html` (`login-view`, `list-setup-view`, `timeline-view`, `profile-view`, `info-view`), all five marked `class="hidden"` in the static markup — there is no router or framework, and no view is visible-by-default at first paint. Exactly one is visible at a time, enforced by a single `showView(view)` helper (`VIEWS.forEach(hide); show(view);`) that every handler calls instead of hiding/showing sections by hand — `init()`'s bootstrap explicitly calls `showView(el.loginView)` in every branch where it isn't resuming a session (no stored token, an auth error, a failed code exchange) rather than relying on the HTML to show login by default; `login-view` used to lack the `hidden` class for exactly that "default" reason, but since `startSession()` awaits a network round-trip (`verify_credentials`) before switching to the timeline, that made the login page visibly flash for a moment on every reload of an already-logged-in session — that hand-rolled approach is what caused a real bug (logging out from the Info page left it visible behind the login form, because the logout handler's manual hide-list didn't include `infoView`); always add a new view to the `VIEWS` array rather than hiding/showing it directly. `#session-info` (the header's action buttons) is a separate concern from the five views, not part of `showView()` — and unlike the views, its five buttons aren't toggled as a group. In DOM/visual order: `timeline-btn`, `profile-btn`, `change-list-btn` ("Settings"), `info-btn`, `logout-btn`. `timeline-btn`, `profile-btn`, `change-list-btn`, and `logout-btn` are individually shown/hidden based on login state (they need a session to mean anything), but `info-btn` has no `hidden` class anywhere and is never toggled — it's always visible, logged in or not, since `#app-header` itself is never hidden. `info-view` is a static "About Mastofoto" page (feature list, an "Accessibility" summary, a "Security & data" summary written for end users — keep both in sync in plain language whenever the actual behavior changes elsewhere in this file, and link to the GitHub repo); its own "Home Page" button is the only way back. There are two ways in, both wiring to the same `showView(el.infoView)` call: the always-visible header `info-btn`, and `login-info-btn`, a link inside the login page's disclosure text (redundant with the header button now that it's unconditionally visible, but kept since it reads naturally as part of that sentence).

**"Home Page" navigation:** `list-setup-view` and `info-view` each have a `.home-link` element (`list-setup-home-btn`/`info-home-btn`) that used to be a plain `<a href=".">` — that caused a full page reload just to get back to a view that was already loaded in memory (re-fetching `app.js`, re-running `verify_credentials`, and re-fetching the timeline from scratch via `selectList()`), a visible lag compared to the instant, in-memory `showView()` call every other navigation in the app already uses (e.g. the header's Settings/Info buttons). Both are now `<button>`s wired to a shared `goHome()` (right next to `showView()`), which picks the destination from current session state rather than tracking "previous view" history: no session → `loginView`; logged in with a list already loaded → `timelineView` (reusing whatever is already rendered, no refetch); logged in but no list chosen yet (still mid-initial-setup) → back to `listSetupView`, since there's nothing else to show. `.home-link`'s CSS is a button reset (`background/border/padding/margin` cleared, `cursor: pointer`) layered under the same visual styling (`color: var(--link)`, no underline) it had as a link, matching the existing `.link-button` convention used by `login-info-btn`.

**Auth flow (OAuth2, standard redirect):**
1. `REDIRECT_URI` is computed once at load time as `window.location.origin + window.location.pathname` — it always points back at wherever the page is currently being served from, so no URL is hardcoded and the flow works unmodified on GitHub Pages, a custom domain, or `http://localhost` during local testing. This is also why a `file://` origin doesn't work: Mastodon requires a real, matching redirect URI.
2. User enters an instance domain. If no app credentials exist yet for that instance, `registerApp()` calls `POST /api/v1/apps` to dynamically register the app (with `REDIRECT_URI`) and stores `client_id`/`client_secret`; the instance name and a random `state` (from the local `randomUUID()` helper, not `crypto.randomUUID()` directly) are stashed in `localStorage` under `PENDING_INSTANCE_KEY`/`PENDING_STATE_KEY`, `state` is included in the authorize URL, and the whole page navigates to the instance's `/oauth/authorize` URL (`window.location.href =`, not a popup/new tab). `crypto.randomUUID()` requires a secure context (HTTPS, or `http://localhost`) and is `undefined` otherwise — this broke login with `crypto.randomUUID is not a function` when testing from a real phone over a plain `http://<lan-ip>:port` origin (works fine from `http://localhost`, per the testing instructions below, since that's still a secure context). `randomUUID()` calls `crypto.randomUUID()` when available and otherwise builds a v4 UUID by hand from `crypto.getRandomValues()`, which — unlike `randomUUID()` itself — has no secure-context restriction.
3. Mastodon redirects the browser back to `REDIRECT_URI` with `?code=...&state=...` (or `?error=...` if the user declines). On load, `init()` reads those query params, calls `completeAuthorization(code, returnedState)` — which requires `returnedState` to exactly match the stored `PENDING_STATE_KEY` (both pending keys are consumed/cleared regardless of outcome, so this check only ever accepts a code that was in flight from a login this same browser just started, closing a login-CSRF gap), then looks up the pending instance and its stored `client_id`/`client_secret`, exchanges the code via `exchangeCodeForToken()` (`POST /oauth/token`), and starts the session. The query string is stripped with `history.replaceState()` before any of this so the code/state aren't left in the URL/history.
4. Scope requested is `read write:favourites write:statuses` — enough for reading lists/timelines and for favouriting/reblogging, deliberately excluding general posting.

All credentials (`clientId`, `clientSecret`, `accessToken`, `listId`) are namespaced per-instance in `localStorage` via `storageKey(instance, name)` (`mastofoto:<instance>:<name>`), plus a `mastofoto:lastInstance` pointer used to auto-resume a session on load. Because there is no backend, the client secret is necessarily exposed in the browser — acceptable for this single-user use case but worth remembering if the scope of the app ever changes. Note that switching hosting origins (e.g. testing on `localhost` after having registered the app on the production URL) invalidates the cached `client_id`/`client_secret` for that instance, since Mastodon validates the redirect URI against what the app was registered with — clear that instance's localStorage entries (or log out) if authorization starts failing after a hosting change.

**Service worker:** `sw.js` (repo root, so its scope covers the whole app regardless of hosting path) caches the static shell only — `index.html`, `style.css`, `app.js`, `manifest.json`, the logo/favicon — never API responses (the fetch handler bails out on any cross-origin request, which covers every Mastodon API call automatically since those always hit `https://${instance}`). It's **network-first, cache-as-fallback**, not cache-first: every same-origin GET tries the network first and updates the cache on success, only falling back to the cache when the network fails. This was a deliberate choice given how often this project ships releases — a naive cache-first strategy would need its `CACHE_NAME` bumped in lockstep with every release (like `APP_VERSION`) to avoid serving a stale app indefinitely; network-first self-heals instead, so `CACHE_NAME` only needs bumping if the shell file list itself changes. Registered from `app.js` behind an `if ('serviceWorker' in navigator)` check, after `window.load`.

**Blurhash placeholders:** `decodeBlurhash()`/`blurhashToDataUrl()` in `app.js` are a from-scratch reimplementation of the public blurhash algorithm (https://blurha.sh) — deliberately not the npm package, to keep the app dependency-free. `buildMediaElement()` decodes each image's `att.blurhash` into a small (32×32) canvas, and sets the result as the `<img>`'s CSS `background-image` (cleared on `load`) so a blurred preview shows while the full-resolution file downloads. This needed `data:` added to the CSP's `img-src` (still no change to `script-src`/`style-src`, so it doesn't loosen anything script-execution-relevant). The `<img>` also gets `width`/`height` HTML attributes from `att.meta.original` (falling back to `att.meta.small`) — set from the image's own true dimensions, not a cropped/different ratio, so this only reserves layout space and lets the blurhash placeholder actually be visible before load; on a single-photo post nothing crops it further (see **Multi-photo grid** below for the one case that does). If the full-resolution file fails to load (dead URL, network error), the browser's own native broken-image icon — and, on some mobile browsers, a visible border/alt-text box — would otherwise appear on top of the blurhash background, since that background-image is a separate layer from the `<img>`'s own (failed) foreground content. `TRANSPARENT_PIXEL` (a 1×1 transparent PNG `data:` URI) is swapped into `img.src` on the `error` event specifically to prevent this: a tiny image that loads successfully replaces one that failed, so the element counts as "loaded" and the native broken-image chrome never renders, leaving the blurhash blur as the only visible result. This must **not** go through the same `load` listener that normally clears the blurhash background (that would defeat the point — the blur would vanish the instant the transparent placeholder itself finishes loading) — the blurhash's `load` listener is captured as a named `clearPlaceholder` function specifically so the `error` handler can `removeEventListener` it before swapping `src`, rather than being a throwaway arrow function as before. `alt` text is untouched by any of this and stays available to assistive technology regardless of whether the image data itself ever loaded. That same `error` handler also adds a `media-load-failed` class to the `<img>`, which sets `aspect-ratio: 4 / 3` in `style.css` — on a single-photo post the box would otherwise keep reserving space at the *original* photo's own aspect ratio (from the `width`/`height` attributes above), which can be a tall box for a portrait shot; once there's no photo left to ever show there, only the blurhash placeholder, a tall reserved box just wastes feed space for no benefit, so the failure case forces the same shorter, fixed 4:3 ratio the multi-photo grid already uses below (a no-op there, since it's already 4:3, not a conflict). The same `TRANSPARENT_PIXEL` constant (plus a shared `setImgErrorFallback(img, fallbackSrc)` helper wrapping the identical `addEventListener('error', ..., { once: true })` pattern) is reused for custom emoji `<img class="emoji">`s — there's no blurhash to preserve there, so a failed emoji just quietly disappears instead of leaving an inline broken-image glyph in the middle of a sentence. Account avatars use the same helper with a different fallback, `AVATAR_FALLBACK` (`assets/favicon.png`), instead: a broken avatar shows the app's own icon rather than either the native broken-image icon or nothing. Because the post header (`header.innerHTML`, one avatar), the list-members preview (`item.innerHTML`, one avatar plus a possible emoji in the display name), and a status card's body (reblog banner, content-warning summary, and the post content itself — all independently `.innerHTML`-templated, each potentially containing emoji) build their markup as HTML strings rather than individual `createElement()` calls, the fallback can't be wired inline (a `<img onerror="...">` attribute would be blocked outright by this app's `script-src 'self'` CSP, which has no `'unsafe-inline'`) — instead each call site queries the already-inserted element(s) right after setting `innerHTML` and attaches the listener in JS. For a status card specifically, this is done **once**, in a single `card.querySelectorAll('img.emoji')` pass just before `renderStatusCard()` returns — after the header, banner, and body have all already been appended to `card` — rather than repeating the same query separately after each of those three `.innerHTML` assignments.

**Multi-photo grid:** a post with more than one photo gets different treatment than a single-photo post. `buildMediaElement()` already builds a `photos` array (images only, since Mastodon's own server-side validation never lets a status mix image attachments with a video/gifv/audio attachment — a status is either 1-4 images, or exactly one video/gifv/audio, so `photos.length` is always an accurate, unambiguous count to key off of). When `photos.length > 1`, the `.status-media` container gets an extra `status-media-grid` class and a `--media-columns` custom property, set from `mediaGridColumns(photos.length)` (`pure.mjs`, DOM-free and covered by `pure.test.mjs`): 3 columns when the count divides evenly by 3, otherwise 2 — a plausible default, not an attempt at perfectly equal rows for every count (5 photos, for instance, still ends up with a shorter last row, which is accepted rather than special-cased). `.status-media-grid img, .status-media-grid video` then get `aspect-ratio: 4 / 3` + `object-fit: cover` in `style.css`, forcing every tile to the same crop instead of its natural aspect ratio. Because `grid-template-columns: repeat(var(--media-columns, 2), minmax(0, 1fr))` uses equal-width tracks across the *whole* grid (not per-row), every tile — including a lone item in a shorter last row — gets the same column width and therefore, with the aspect ratio fixed, the same height too; no extra "make the last item span full width" rule is needed. The `minmax(0, 1fr)` (rather than a bare `1fr`, which resolves to `minmax(auto, 1fr)`) is required, not cosmetic: a grid track's `auto` minimum falls back to its content's intrinsic size, and a raw photo `<img>` carries `width`/`height` HTML attributes reflecting its full resolution (see above) — often thousands of pixels — so without the explicit `0` floor the grid would size its columns to the photo's real dimensions and overflow the card sideways on mobile, exactly like the pre-existing single-column rule already avoids via its own explicit `minmax(140px, 1fr)`. A single-photo post never gets `status-media-grid` and keeps rendering exactly as before: full aspect ratio, uncropped.

**Logo & favicon assets:** `assets/logo.png` is a pre-rendered transparent PNG of the word "Mastofoto" set in the Google Font "Pacifico" — it exists specifically so the page never has to load a webfont at runtime. `assets/favicon.png`/`assets/favicon.ico` are the same treatment applied to just the letter "M", cropped/centered to fill the icon square. Both were generated with Pillow (`ImageFont.truetype` + `ImageDraw.text`, measuring the glyph's `textbbox` to scale and center it before rendering) from the actual Pacifico TTF (fetched from `fonts.gstatic.com`), not with a browser. To regenerate either (e.g. a different color/size), re-run that kind of script rather than trying to reintroduce a `<link>` to Google Fonts. `assets/favicon.png` itself stays transparent and is used only for the browser-tab `<link rel="icon">`s — a transparent icon reads fine at that tiny size against a browser's own tab chrome. The mobile/PWA home-screen icon is a separate asset, `assets/app-icon.png` (referenced by the `apple-touch-icon` `<link>`, and by `manifest.json`'s 512×512 `purpose: "any"` entry), because a transparent icon looks inconsistent once a phone's launcher composites it over an arbitrary wallpaper — it needs an opaque background baked in. `app-icon.png` is generated by alpha-compositing the unmodified `favicon.png` (same blue "M", same color, untouched) over a diagonal linear gradient from `#232a32` (top-left) to `#12151a` (bottom-right) — dark tones centered on the app's own dark-theme background `#191d20`, chosen so the brand blue "M" (`#2b90d9`) keeps ≥4.2:1 contrast against every point of the gradient (computed with the WCAG relative-luminance formula, the same method used for the theme's other contrast checks) while still reading as a deliberate, on-brand "glossy dark" icon rather than a flat fill. If the icon ever needs regenerating, reproduce that same composite (transparent `favicon.png` over the gradient) rather than re-drawing the letter from scratch, and re-check contrast if the gradient colors change.

`manifest.json` also lists two more icons built from these same two source assets, added for full PWA-installability polish (not required for the app to already be installable — a manifest with just the one 512×512 icon already satisfies that — but recommended for broader launcher/tooling compatibility): `assets/app-icon-192.png` (`purpose: "any"`) is a plain Lanczos downscale of `app-icon.png` to 192×192, since some install-prompt UIs and older tooling specifically look for a 192px icon rather than downscaling the 512px one themselves. `assets/app-icon-maskable.png` (`purpose: "maskable"`) is a **separate composite**, not a re-tagged copy of `app-icon.png` — a maskable icon needs its important content to stay within a centered "safe zone" (the standard guidance is roughly an 80%-diameter circle) since Android launchers crop maskable icons into varying shapes (circle, squircle, rounded square, ...) and anything outside that zone can get clipped. Measuring `app-icon.png`'s actual glyph bounding box showed its corners sitting almost exactly on that 80% boundary (~205px from center vs. a 204.8px safe radius at 512px) — safe for a plain square icon, but too tight to also declare `maskable` as-is without risking the letter's edges being cut off by a circular mask. The maskable variant crops the "M" out of `favicon.png` by its bounding box, scales it down to 78% before recentering it on a transparent 512×512 canvas, and composites *that* over the identical gradient (regenerated pixel-for-pixel from the same two hex endpoints, not reused from `app-icon.png`, so there's no dependency on the non-maskable file for this step) — landing its bounding box corners at ~160px from center, comfortably inside the safe zone. Because the color and gradient are both unchanged from `app-icon.png`, the already-established ≥4.2:1 contrast finding (checked against *every point* of the gradient, not just the old glyph position) still holds without needing to be re-verified for the new glyph position/size. If regenerating, reproduce the same two-step process (crop+scale+recenter the glyph, then composite over a freshly-generated instance of the same gradient) rather than shrinking the finished `app-icon.png` in place, which would shrink the background gradient along with the glyph and change the composite's framing.

Both new icon files are also listed in `sw.js`'s `SHELL_FILES` (see **Service worker** above) alongside `app-icon.png` itself, which — a pre-existing gap, not introduced by this change — had never actually been in the shell cache list despite being referenced by `index.html`'s `apple-touch-icon` link and the original manifest entry; adding all three together bumped `CACHE_NAME` to `mastofoto-shell-v2`, per the versioning rule in **Service worker** above (bump only when the shell file list itself changes).

**Header action "buttons" styled as links:** `#session-info`'s "Settings"/"Log out" and the info button are deliberately still `<button>` elements, not `<a>` — they trigger an in-page view switch or clear session state, they don't navigate to a URL, and a real `<button>` is keyboard-operable (Enter/Space, tab order) for free. Only the CSS changed: no background/border, text colored with `--link`, underline appears on `:hover`. Don't add `opacity` to dim them at rest like the old filled-button style did — that was tried and reverted because diluting `--link` with opacity dropped it back under the 4.5:1 contrast minimum in light mode; if a "muted until hover" look is wanted again, pick a distinct, separately-contrast-checked color for the resting state instead of fading the existing one.

**Active nav highlighting:** whichever of Timeline/Profile/Settings(`change-list-btn`)/Info is currently showing gets `#session-info button.active { color: var(--nav-active); }` — text/icon color only, deliberately no background fill (tried first, then explicitly rejected in favor of a text-color-only treatment). `--nav-active` is a dedicated token, themed independently rather than reusing one existing token verbatim in both themes, because no single existing token works as-is in both: `--link` (the hover color) fails in dark mode specifically, since `--link-header` (the resting color) and `--link` are the *exact same value* there (`#5aa9e6`) — no visible difference from resting at all; `--btn-primary-bg` fails in dark mode too, but for a different reason — as *text* against the dark theme's background it measures only ~2.9:1, well under the 4.5:1 minimum (it was only ever verified as a button *fill* against white text, not as text color against a page surface). So `--nav-active` aliases a different existing token per theme: `var(--link)` in light mode (blue, matching the requested look, still >5:1 against the light background) and `var(--text)` in dark mode (the app's full-strength body text color, >14:1 against the dark background, clearly distinct from both the muted resting `--link-header` and the hover `--link` there) — each side just an alias (`--nav-active: var(--link);` / `var(--text);`), not a duplicated hex, so it can never drift from whichever token it points to. `.btn-icon`'s usual resting dim (`opacity: 0.7`, chosen for the plain-link look) is overridden back to full opacity under `.active`, same reasoning `.status-actions`/`.reblog-banner` already override it elsewhere — dimmed, the icon would read weaker than the now-full-strength label text next to it. Login-view has no persistent nav button, so nothing is highlighted while there. Wiring lives entirely in `showView()` — a `VIEW_NAV_BUTTONS` map (`view` → its nav button, only for the four views that have one) is walked on every call, toggling `.active` and `aria-current="true"`/removed accordingly, so every existing and future navigation path (including `goHome()` and the two "Home Page" buttons) stays correctly in sync without each call site needing to know about it. `aria-current` carries the same "you are here" signal to screen readers, since the visual highlight alone wouldn't reach them.

**Icons:** every icon in the app (the header's Settings/Info/Log out, and the feed's Favourite/Reblog/View post buttons plus the "boosted" banner) is a small inline `<svg>` (in a `<span class="btn-icon" aria-hidden="true">` wrapper, `.btn-icon svg` fixed at 16px, `.btn-icon svg { display: block; width/height }` in `style.css`) rather than an emoji or an external image file. All of them use `stroke="currentColor"` (with a couple of small `fill="currentColor"` accents, e.g. the Settings icon's dots) instead of a fixed color, specifically so they inherit whatever CSS `color` the surrounding button/text already has — the header's `--link-header`/`--link` on hover, or the feed buttons' `--text` at rest and `--accent-contrast` when `.active` (favourited/reblogged) — and so both light and dark theme are covered automatically with one asset instead of two. Being inline markup rather than `<img src="icon.svg">` files, they add effectively no page weight and can react to CSS in a way an external SVG file referenced by `<img>` cannot. The feed action buttons keep their visible count in a separate `<span class="btn-count">`, updated on click by `toggleFavourite()`/`toggleReblog()` via `btn.querySelector('.btn-count').textContent = ...` — don't go back to overwriting the whole button's `textContent`, since that would destroy the icon `<span>` along with the count. `.status-actions .btn-icon`/`.reblog-banner .btn-icon` override the header's `.btn-icon { opacity: 0.7 }` back to full opacity, since that dimming was chosen for the header's plain-link look and isn't appropriate on the feed's solid-background buttons. The now-unused `.icon-btn` CSS rules (from an earlier, pre-SVG version of the header buttons) were removed — don't reintroduce them. The login page's `.feature-checklist` reuses this same inline-SVG-with-`currentColor` pattern for its three checkmark bullets, tinted via `.check-icon { color: var(--link); }` rather than a new color token — it's a decorative accent at icon size, not body text, so it doesn't need its own contrast-checked token the way `--link`/`--btn-primary-bg` do for actual text/button-fill use.

**Theme (light/dark):** every color in `style.css` is a CSS custom property, defined on `:root` (light, the default) and re-declared under `:root[data-theme="dark"]` — no bare hex/rgba should appear outside those two blocks; a new color needs a token added to both, even if the value is identical in both themes (e.g. `--btn-primary-bg`, `--accent-contrast`, `--overlay-bg` don't change between themes, but stay tokenized for consistency and so every color has exactly one place to look it up). The background asked for specifically was `#191d20`. `--shadow` is the one value that *does* differ non-trivially — `.card`/`.status-card`'s box-shadow is bumped to a higher opacity in dark mode since a shadow the same strength as light mode barely reads against a dark page. `app.js` computes the effective theme once at startup (`getPreferredTheme()`): an explicit choice in `localStorage` (`mastofoto:theme`) wins, otherwise it falls back to `prefers-color-scheme`. `applyTheme()` sets the `data-theme` attribute on `<html>` and also updates the `<meta name="theme-color">` tag so the mobile/PWA chrome matches. The picker lives in Settings (`#theme-select`) as a plain `<select>`, seeded with the effective theme on load and persisting explicitly on `change` — there's no "system/auto" option once a user has picked one, and no listener for the OS preference changing while the app is open (out of scope; re-opening the app or re-toggling covers it). The login page's `.login-form` panel (framing the instance-domain field and Connect button) reuses `var(--bg)` — the page background token, not `--surface` — as its own background specifically because it sits inside a `.card`, which is already `--surface`; since `--bg` and `--surface` deliberately invert their relative lightness between themes (light mode: `--surface` `#fff` lighter than `--bg` `#f2f3f5`; dark mode: `--surface` `#22262b` lighter than `--bg` `#191d20`), reusing `--bg` here reads as a subtly recessed inset box in both themes without needing a third, dedicated token.

**Post text size:** a second Settings control, right below the theme picker, lets the user scale post body text independently of the theme — `#font-size-slider`, a native `<input type="range" min="-0.5" max="0.5" step="0.1">` representing an *offset* in `rem` from the default `1rem`, not an absolute size. `getPreferredFontSizeOffset()`/`applyFontSizeOffset()` mirror the theme functions exactly (localStorage key `mastofoto:postFontSizeOffset`, applied once at startup before login), except the value is written to a single CSS custom property (`--post-font-size`, consumed by `.status-content { font-size: var(--post-font-size, 1rem) }` and the Settings-page live preview `.font-size-preview`) rather than an attribute, since a numeric range has no `data-*`-friendly discrete states the way light/dark does. The slider fires on `input`, not `change`, so both the persisted value and the live preview update continuously while dragging rather than only on release. Tick marks are a hand-drawn overlay (`.font-size-slider-wrap > .font-size-ticks`, 11 `<span class="tick">`s laid out with `justify-content: space-between`, one per 0.1 step, the center one distinguished as `.tick-default`) rather than a `<datalist>` — a first attempt used `<datalist>`, but its native tick rendering is too subtle to notice in Chrome/Firefox/Edge and doesn't render at all in Safari; a manually drawn row underneath the track (inset 8px each side to roughly match the thumb's own travel inset) looks identical and equally visible in every browser. It's `aria-hidden="true"` and `pointer-events: none` since it's a purely visual ruler — the slider's own native `step` is what actually makes the thumb snap, independent of any visual tick. Deliberately **no numeric readout** next to the slider, since the ticks plus the live preview text were judged sufficient feedback and a number was considered visual clutter for an 11-step range centered on an obvious, distinctly-colored middle tick. The preview text (`.font-size-preview`) is `aria-hidden="true"`: it's a sighted-only convenience, since a screen reader user already gets the current value announced by the native range input itself and doesn't need a redundant sample sentence read aloud. `Math.round(value * 10) / 10` guards against binary floating-point drift (e.g. `0.30000000000000004`) before the offset is persisted or applied.

**Brand blue vs. accessible blue:** `#2b90d9` (the literal brand color baked into `assets/logo.png`/`assets/favicon.png` and `manifest.json`'s `theme-color`) measures only ~3.45:1 against white, short of the 4.5:1 normal-text requirement — so it is used **only** for those non-text, decorative contexts and is deliberately **not** a CSS variable in `style.css`. Every place that needs actual contrast uses one of two separate, accessible tokens instead: `--btn-primary-bg` (`#1c69a0`, identical in both themes — button-fill contrast against its own white label doesn't depend on the page theme, since the button *is* the immediate background) for solid buttons/`.new-badge`/the active favourite-reblog state, and `--link` (`#1a6699` light / `#5aa9e6` dark — a link's background *is* the page surface, which does change per theme, so this one can't share a single value like `--btn-primary-bg` does) for inline text links and the photo focus-visible outline. Don't reintroduce `#2b90d9` (or a `var(--accent)`-style alias for it) into any text- or button-fill rule — that's exactly the contrast failure this split fixed.

**Accessibility:** contrast has been checked by computing actual WCAG ratios (not eyeballed) for every token pair — `--text-tertiary`, `--border-strong`, `--btn-primary-bg`, and `--link` were all measured failures in the original palette (before the brand/link split above) and are now tuned to pass (≥4.5:1 for text, ≥3:1 for UI component borders) in both themes; re-verify with the relative-luminance formula (not intuition) if any of these tokens change again. The page has exactly one `<h1>` (`.sr-only`, "Mastofoto", in the header, present across all views since the header itself never hides) with each view's own heading correctly nested under it as `<h2>`/`<h3>`/`<h4>` — don't add a second `<h1>` if a view's title ever needs promoting for some other reason.

**Responsive layout:** all mobile overrides live in a single `@media (max-width: 480px)` block at the very end of `style.css`, rather than scattered near each base rule — this matters because a media query has the same specificity as the plain selector it targets, so with equal specificity the rule *later in the file* wins regardless of the media query; keeping the block at the end guarantees every override comes after its unconditional base rule. Notable overrides: `#session-info`'s five buttons (Timeline, Profile, Settings, Info, Log out) all wrap their label in `<span class="btn-icon">`/`<span class="btn-label">`, and the mobile rule hides `.btn-label`, leaving just the icon (sized up via `#session-info .btn-icon svg { width/height: 20px }`, since the icons are fixed-size inline SVG rather than a font glyph `font-size` could scale) in the same tap-target area used at desktop width; `#session-info`'s own `gap` also drops from the desktop 12px to 6px in this block — with five icon-only buttons instead of the original three, 12px left essentially no spare width next to the logo on a 320px-wide viewport, so the gap (not the 28px tap targets themselves) is what shrinks; `.status-author .username` gets a fixed `width: 195px` with `overflow: hidden` and a right-edge `mask-image` fade (`-webkit-mask-image` too, for Safari) instead of the shared `text-overflow: ellipsis` — chosen specifically so its width never depends on how much room the corner-pinned date needs on the same row, which a flex-shrinking width would (see **New-post highlighting** below for why that row no longer wraps on mobile at all). Don't reintroduce a second `@media (max-width: 480px)` block elsewhere in the file — add new mobile rules to the existing one at the bottom. The login page's `.login-columns` wraps the feature checklist and `.login-form` in a `display: flex` row so the two sit side by side above the mobile breakpoint (`flex: 1; min-width: 0` on both children, the same overflow-safe pattern as `.member-info`/the multi-photo grid) — the mobile override switches it to `flex-direction: column` and moves the two children's bottom margins back onto themselves (removed at the row level, where side-by-side siblings don't need one) to restore the original stacked spacing.

**Timeline configuration:** the app intentionally supports exactly one active timeline at a time (not a multi-list browser) — but that one timeline can be either a Mastodon list or the account's Home timeline. `showListSetup()` always prepends a `<option value="home">Home timeline</option>` to `#list-select` (`HOME_TIMELINE_ID = 'home'`, a sentinel string that can never collide with a real numeric list id) before fetching `/api/v1/lists` and appending one option per list; the choice is persisted as `listId` per-instance (so the sentinel string `'home'` is what ends up stored when that's picked) and reused on future logins — `startSession()`/`el.changeListBtn`'s handler treat it exactly like a real list id, since nothing about resuming a saved choice needs to know which kind it is. Home timeline requires no extra OAuth scope beyond the `read` already requested. The "Settings" button (`change-list-btn` — the id is unchanged from before the rename, still just opens `#list-setup-view`) re-opens the same screen to switch later; that screen also holds the theme picker (see **Theme** below), unrelated to any single Mastodon list/instance. When a real list is selected, that screen previews its membership via `loadListMembers()` (`GET /api/v1/lists/:id/accounts?limit=80` — a single page, no pagination, since these are meant to be small curated lists), sorted alphabetically by `display_name || username` with `localeCompare(..., { sensitivity: 'base' })`; `updateListPreview(listId)` is the single gatekeeper for this — it calls `loadListMembers()` for a real list id, or just clears/hides the members list when `listId` is falsy or the home sentinel, since "membership" isn't a concept the Home timeline has. It runs on the select's `change` event and once right after the dropdown is first populated in `showListSetup()`. The list has no `max-height`/scroll of its own — it renders in full and lets the page scroll. The whole preview is a native `<details id="list-members-heading">`/`<summary>Members</summary>` disclosure, collapsed by default — clicking "Members" expands `#list-members` with zero JS for the open/close mechanic itself (keyboard-operable for free too), the same `<details>`/`<summary>` pattern content-warning posts already use (see **Rendering & sanitization** below). `el.listMembersHeading` still refers to the outer `<details>` (the id didn't change even though the tag did), so the existing `show()`/`hide()` calls that gate *whether the preview exists at all* (real list vs. Home timeline/no selection) keep working unchanged — that's an orthogonal concern from the `<details>`'s own native `open` state, which only governs whether an existing, shown preview is currently expanded. `loadListMembers()` explicitly resets `el.listMembersHeading.open = false` before repopulating, so switching from one list to another always starts collapsed again rather than inheriting whatever expand state was left over from the previously-selected list. Each member's name is linked to `account.url` (profile), same `isHttpUrl()`-guarded fallback-to-plain-text pattern as the post author links; the name and `@handle` are wrapped together in a `.member-info` element so their relative layout can change per breakpoint without touching the surrounding `<li>` — on desktop it's a flex row (name and handle side by side, as before), but on mobile the fixed `@media (max-width: 480px)` block switches it to a column (handle below the name) since a long display name plus a long handle on one line could overflow the row on a narrow screen; both `.member-name` and `.member-handle` also get `overflow-wrap: anywhere` so a single very long unbroken name or handle can't do the same on its own. If a Mastodon account has no lists at all, `#no-list-message` still only hints that lists are optional (rather than blocking setup) since Home timeline is always a usable option regardless.

**Timeline & photo filtering:** Timeline's feed engine (see **Lazy loading** below) fetches `/api/v1/timelines/home` when `state.currentListId === HOME_TIMELINE_ID`, otherwise `/api/v1/timelines/list/:id`; neither endpoint has a server-side "exclude reblogs" param (only `max_id`/`since_id`/`min_id`/`limit` are documented for these two, unlike `/api/v1/accounts/:id/statuses` which does have `exclude_reblogs` and `only_media` — see **Profile** below, the one place in this app that *does* use that endpoint), so whether boosts appear is a client-side filter instead: `statuses.filter(s => (includeReblogs || !s.reblog) && hasPhoto(s))`, where `includeReblogs` comes from `getPreferredIncludeReblogs()` (see **Feed content settings** below). With the setting turned off (it's on/boosts-included by default), a boost is excluded outright, even one boosting a status with a photo — `hasPhoto()` itself is untouched and still correctly reblog-aware (it looks at `status.reblog`'s own media, per its `pure.test.mjs` coverage), that behavior just isn't reached through this call site when `!s.reblog` already excludes anything it would have needed to look inside a reblog for. Either way it paginates using the `Link: rel="next"` header (falling back to the last returned status id via `parseNextMaxId()`). This filtering happens after pagination, so a single fetched page can yield zero photo posts — more likely on Home timeline than on a small curated list (mixes in every followed account's non-photo posts too), and more likely still with the boosts setting turned off, since boosts no longer count as usable content even when they carry a photo. There is no "Load more" button; scrolling near the bottom (or a short feed already fitting on screen) triggers the engine's own `maybeLoadMore()`, which keeps calling `load(true)` on its own — via mutual recursion, not a tight loop, so the tab stays responsive — until a page actually yields a photo or that feed's cursor is exhausted, capped by `MAX_CONSECUTIVE_EMPTY_PAGES` (20) as a backstop against a pagination bug or a pathologically photo-sparse (or boost-heavy, with the setting off) timeline turning into an unbounded chain of requests. This mechanism doesn't care *why* a page came up short — a page of text-only posts and a page of all-boosts hit the exact same code path — so excluding boosts needed no changes to the loading/pagination machinery itself, only to the filter predicate. Pagination's own cursor is derived from the raw, unfiltered `statuses` array regardless, so none of this affects paging correctness either. See **Lazy loading** below for the full mechanism, including why this isn't just `load(true)` called straight from an `IntersectionObserver` callback.

**Profile:** a second, independent feed — the logged-in account's own photo posts — reachable via the header's `profile-btn`, showing side by side with (never replacing) whichever list/Home timeline is selected. Its `createFeedEngine()` instance (`profileFeed`) fetches `GET /api/v1/accounts/${state.accountId}/statuses?only_media=true&exclude_reblogs=true&limit=20[&max_id=...]` — `state.accountId` comes from `verify_credentials`'s response body, which `startSession()` now actually parses (`const account = await res.json(); ...; state.accountId = account.id;`) rather than discarding it as before. `exclude_reblogs=true` is unconditional here, deliberately **not** wired to `getPreferredIncludeReblogs()` — that setting only ever means "boosts in my Timeline," Profile is "posts I actually published," so the two must never be conflated. `only_media=true` filters to *any* media attachment, not specifically images (per **Multi-photo grid** below, a status can carry 1-4 images or exactly one video/gifv/audio) — so `filterStatuses: statuses => statuses.filter(hasPhoto)` still runs client-side on top of it; this is a real, load-bearing filter, not redundant belt-and-suspenders, since an own-post that's video-only would otherwise pass the API's own_media check and get rendered. Profile's `renderCard` calls `renderStatusCard(status, false, false, false)` — always `isNew: false` (no "New" badge, and it structurally never could be one since this is always `false` — see **New-post highlighting**), `showActions: false` (suppresses `renderStatusCard()`'s Favourite/Reblog button construction entirely; the "View post" link/button is unconditional regardless of `showActions`, so it's the only action Profile cards keep), and `showAuthor: false` — every Profile card is unavoidably the logged-in account's own post, so repeating its own avatar/display-name/handle on every single card is pure noise there; only the date remains (see **Rendering & sanitization** below for the layout consequence of dropping the rest of the header). No pull-to-refresh element exists in `profile-view` — v1 scope is deliberately just a read-only, lazily-paginated photo grid, which is exactly why `ensureLoaded()`'s success/failure handling matters more here than it would for a feed with another way to retry: `hasLoadedOnce` is only set to the *result* of `load(false)` (`load(false).then(ok => { hasLoadedOnce = ok; return ok; })`), not unconditionally before the fetch even starts — a version that set it eagerly would permanently latch "already loaded" after a single failed first attempt (network blip, instance hiccup) and never call `load()` again for the rest of the session, since Profile has no pull-to-refresh to fall back on the way Timeline does. `profile-btn`'s click handler calls `showView(el.profileView)` then `profileFeed.ensureLoaded()` — a genuine no-op only after a *successful* first visit, so revisiting Profile never refetches or loses scroll-independent state (mirroring how Timeline's own content persists across navigating to Settings/Info and back), but a failed visit is retried the next time the button is clicked. `reset()` also hides that engine's `errorEl` as part of clearing state, so a stale error message can't outlive the state it described. Logging out calls `profileFeed.reset()` (alongside clearing `state.accountId`) specifically so a second account logging in on the same browser can never see the first account's cached Profile photos before its own first fetch completes. `timeline-btn`'s click handler is `goHome()`, not a bare `showView(el.timelineView)` — a first-time user still mid-initial-setup (no list/timeline chosen yet, `state.currentListId` still `null`) has no timeline content to show, and `goHome()` already knows to send them to `listSetupView` instead in that case, the same fallback the "Home Page" links use; a bare `showView(el.timelineView)` would have shown a silently blank feed instead.

**Profile banner:** `#profile-banner`, above the post grid in `profile-view`, shows the account's own Mastodon cover photo (`account.header_static`, falling back to `account.header`) with the avatar, display name, and `@handle` overlaid directly on top of it (not below/overlapping its edge). `startSession()` computes `profileBannerData` (`{ header, avatar, displayNameHtml, username }`) once from the `account` object — `displayNameHtml` via `renderEmojiText()`, same as every other display name in the app (post header, list-members, reblog banner), for custom-emoji support — but does **not** touch the DOM directly. `populateProfileBanner()` is the only thing that actually writes `profileBannerData` into `#profile-banner-image`/`-avatar`/`-displayname`/`-username`, and it's called only when the banner is actually going to be visible: once from `startSession()` if `getPreferredShowProfileBanner()` is already true, and again from `applyShowProfileBanner(true)` if the setting gets turned on later. This matters because assigning an `<img>`'s `src` fires a real network request the instant it happens, regardless of any `.hidden` ancestor (CSS visibility doesn't defer image loading) — populating unconditionally in `startSession()` (an earlier version of this code did) meant the cover photo and avatar were downloaded on every login even with the setting off, or with Profile never once opened that session; gating the population itself on the setting, not just the element's visibility, fixes that. The handle is set via `textContent`, not `innerHTML`, since it's never anything but plain `@acct` text; the display name, since it *can* contain emoji `<img>` tags from `renderEmojiText()`, gets the same `querySelectorAll('img.emoji').forEach(setImgErrorFallback(...))` pass every other emoji-bearing `innerHTML` assignment in the app already gets (a first version of this code missed this, which would have shown the native broken-image icon inline in the banner name for a dead custom-emoji URL — exactly the class of bug **Blurhash placeholders** above was written to eliminate everywhere else). Both images otherwise reuse that same existing broken-image handling: `setImgErrorFallback(el.profileBannerAvatar, AVATAR_FALLBACK)` (same as every other avatar in the app) and `setImgErrorFallback(el.profileBannerImage, TRANSPARENT_PIXEL)` for the cover photo — a failed (or absent, `profileBannerData.header || TRANSPARENT_PIXEL`, so an account with no cover photo never even attempts a blank-string request) cover photo just falls back to `#profile-banner`'s own `--btn-secondary-bg` background showing through, no broken-image chrome. `#profile-banner-info`'s `background: linear-gradient(to top, var(--photo-scrim), transparent)` is what keeps the `--accent-contrast` (white) name/handle text legible regardless of how bright or dark the underlying cover photo happens to be — `--photo-scrim` is a new token, deliberately identical in both themes (same rationale as `--overlay-bg`, already used by the lightbox: it's compositing over arbitrary user-photo content, not the app's own surface, so it shouldn't follow the app's own light/dark palette). The banner box itself is a fluid `aspect-ratio: 3 / 1` (no fixed pixel height), so it scales with viewport width on its own; the one mobile-specific tweak (avatar `56px` → `44px`, tighter `#profile-banner-info` padding, smaller handle `font-size`) lives in the shared `@media (max-width: 480px)` block per **Responsive layout** below, purely to keep the overlay from feeling cramped at narrow widths, not because the aspect-ratio itself needs to change per breakpoint. `#show-profile-banner-checkbox`, under Profile's "Display" subsection, controls whether it's shown at all — `getPreferredShowProfileBanner()`/`applyShowProfileBanner()` mirror the theme/font-size pattern exactly (a dedicated `applyX()` rather than the plain-checkbox style `#include-reblogs-checkbox` uses, since there *is* persistent visual state to reapply here: a hidden/shown DOM element, not just a value read at fetch time), including being applied once at module init (not gated on login) since hiding an already-hidden `profile-view` costs nothing. `localStorage`'s `mastofoto:showProfileBanner` follows the same `null` → `true` (shown by default) convention as `mastofoto:includeReblogs`. This is deliberately a global, device-wide setting like theme/font-size — not per-account like `profileTags`/`listId` — since it's a layout preference ("do I want this element on screen"), not something tied to a specific account's own data.

**Profile tag filter:** `#profile-tags-input`, under Profile's "Filters" subsection (see **Settings page structure** above), narrows the feed above to only your own posts carrying at least one of a comma-separated list of hashtags — "#cats, #Sunset" and "cats,sunset" are equivalent, since `parseTagFilter()` (`pure.mjs`, DOM-free and covered by `pure.test.mjs`) strips any leading `#`, trims, and lowercases each entry, dropping empty ones from stray commas. Matching is OR (any one listed tag is enough), not AND — `statusMatchesTagFilter()` (also `pure.mjs`) compares against a status's own `tags: [{ name, url }]` array (already present on every Status the API returns, `name` already `#`-free, so both sides of the comparison end up in the same shape with no extra normalization needed at the call site), and is a no-op (matches everything) when the field is empty — the plain "all your photo posts" behavior. Deliberately **not** implemented via the API's own `tagged` query param on `/api/v1/accounts/:id/statuses`: that param only accepts a single tag per request, so it can't do multi-tag OR filtering without firing one request per tag and merging results — a real pagination redesign for little benefit — so `profileFeed`'s `filterStatuses` just re-reads `getInstanceData(state.instance, 'profileTags')` (via `parseTagFilter()`) fresh on every page instead, the same `filterStatuses` hook that already does the `hasPhoto()` pass, no changes needed to the loading/pagination machinery (same "the engine doesn't care *why* a page came up short" property noted in **Timeline & photo filtering** above — a rare tag just means more pages auto-continued through, already bounded by the existing circuit breaker). Stored per-instance via `saveInstanceData`/`getInstanceData` (`profileTags`, holding the raw as-typed string, not the parsed array — parsing happens fresh at filter time) — the same scope as `listId`, deliberately not a global/device-wide setting like theme or font size, since it's a preference about *this account's own posts specifically*. Seeded into the input once per login, in `startSession()`, since it can't be known before `state.instance` is set. Its `change` handler only calls `profileFeed.reset()`, not an eager reload — unlike the reblog checkbox above, Profile is lazy by design (only fetched via `ensureLoaded()` on a visit, never kept warm in the background the way Timeline is), so there's nothing useful to eagerly re-run; the next visit to Profile picks up the new filter naturally. Like `listId`, `profileTags` is deliberately **not** cleared by `clearInstanceData()` on logout — it's remembered for next time you log back into the same account, consistent with how the chosen list already survives logout.

**Settings page structure:** Settings has three `.settings-section`s (Timeline, Profile, Appearance, in that order — Timeline first since it's the one most people reach for most often), each with an `<h3>` title. Profile and Timeline are further split into two `.settings-subsection`s each, labeled with a small muted/uppercase `<h4 class="settings-subsection-heading">` ("Display", "Filters") — a third visual tier below the section title, giving the page a clear read order (section > subsection label > field label > control) rather than a flat list of controls: **Display** holds the plain on/off toggles (Profile's `#show-profile-banner-checkbox`, Timeline's `#include-reblogs-checkbox`); **Filters** holds the settings that determine *what content actually appears* (Profile's tag filter, Timeline's list/Home-timeline picker and its members preview). Appearance's own two controls (Theme, Post text size) still use the older, unlabeled `.sub-settings-section` (just a spacing wrapper, no heading) rather than this newer pattern — they don't split naturally into a "Display vs. Filters" pair, so they were deliberately left as-is rather than forced into it.

**Feed content settings:** `#include-reblogs-checkbox`, under Timeline's "Display" subsection, controls the `includeReblogs` flag above. `getPreferredIncludeReblogs()` reads `localStorage`'s `mastofoto:includeReblogs`: unset (`null`) → `true`, i.e. boosts included by default, matching the checkbox's own `checked` attribute in the static HTML; once a value has been explicitly stored, only the literal string `'true'` reads back as `true` (this asymmetry — `null` defaulting one way, everything else needing an exact match — is what lets "never touched this setting" and "explicitly turned off" both resolve correctly with a single ternary). Deliberately a plain boolean-backed checkbox rather than mirroring the theme/font-size pattern's dedicated `applyX()` function, since there's no persistent visual state to (re)apply on load beyond seeding the checkbox itself. Unlike theme or post text size, toggling this setting changes *what gets fetched and filtered*, not just how already-rendered content looks — so its `change` handler doesn't just persist the value, it also calls `selectList(state.currentListId)` (when a timeline is already active) to force a full re-fetch from scratch, the same reset every list switch already goes through; without this the checkbox would silently do nothing until the next unrelated refresh.

**Lazy loading:** `createFeedEngine(config)` is a factory, not a singleton — `load()` on any one feed is called from multiple independent places (a fresh selection/first visit, pull-to-refresh for Timeline, and auto-continuation while scrolling), so a plain boolean "busy" flag would let one caller silently no-op if it overlapped another (concretely: pull-to-refresh showing "Refreshing…" and resetting the label without an actual refresh happening, if a background auto-load happened to be in flight at that exact moment). Instead every call goes through a shared promise queue private to that engine instance (`queue`, plus a `pendingCalls` *counter* — not a boolean, since two overlapping calls settling out of order would otherwise flip a shared boolean back to "idle" while one is still queued): a call is never dropped, it just waits its turn and then genuinely runs. `load()` is a thin wrapper around the instance's internal `runLoad()` (the actual fetch, returning `true`/`false` for success) that manages this queue and, after every settled call, invokes `maybeLoadMore()` — this single function is what re-triggers auto-paging through a run of zero-photo pages (the sentinel doesn't move, so a passive `IntersectionObserver` alone would never refire) and what auto-fills a short feed right after a fresh load (also no enter/exit transition for the observer to catch). `maybeLoadMore()` re-derives "is the sentinel close enough to load more" itself via a live `getBoundingClientRect()` check (`sentinelNearViewport()`) rather than trusting the observer's own (batched/throttled) entry — the `IntersectionObserver` watching that instance's sentinel element (`rootMargin` sharing the same module-level `AUTO_LOAD_MARGIN_PX` constant used by that check, so the two distances never drift apart) exists only as a cheap "something changed, go re-check" wakeup, since that's far less costly than a manually-throttled raw `scroll` listener. `maybeLoadMore()` checks that instance's own view's hidden state *before* the geometry check — a hidden ancestor collapses the sentinel's rect to all zeroes, which would otherwise misread as "at the very top of the screen" and fire a fetch before a session even exists (each instance's `observe()` call happens at module-eval time, before login). On a fetch error the chain simply stops (no retry loop, matching that an `IntersectionObserver` wouldn't retry on its own anyway) — that instance's own error element shows via the unchanged `showError()`, and recovery is via pull-to-refresh (Timeline) or scrolling away and back. Every one of these properties — the queue, the counter (not boolean), the circuit breaker, the hidden-before-geometry guard order — is per-instance, not shared, so Timeline and Profile can never race or clobber each other's state; there are exactly two live instances today, `timelineFeed` and `profileFeed`, each constructed with its own `{ view, container, errorEl, sentinel, loadMoreEl, buildPath, filterStatuses, onFreshLoad, renderCard }` (see **Timeline & photo filtering** above and **Profile** below for what each instance's config actually does).

**New-post highlighting:** Timeline-only — Profile never tracks this (your own posts don't need a "since your last visit" marker). On every non-append `load()` call on `timelineFeed` (i.e. a fresh list load, not an auto-continuation), that instance's `onFreshLoad` sets the module-scoped `timelineLastSeenBefore` from the previous value of a per-list `localStorage` marker (`lastSeenKey(listId)` → `lastSeen:<listId>`), *before* that marker is overwritten with the newest fetched photo status's `created_at`. `renderStatusCard(status, isNew, showActions, showAuthor)` takes `isNew` as an explicit parameter now rather than reading global state directly — `timelineFeed`'s `renderCard` config computes it fresh from `timelineLastSeenBefore` before each call; `profileFeed`'s `renderCard` always passes `false` (along with `showActions: false` and `showAuthor: false` — see **Rendering & sanitization** below for what those suppress). Profile's `isNew` being hardcoded `false` isn't just "no highlighting happens to apply" — it's structurally impossible for a Profile card to ever get the badge, since nothing in that engine instance ever computes a real value for it. A flagged card gets `is-new` (only used for the `"New"` badge shown next to the timestamp — the card itself is no longer tinted). `.new-badge` and `.status-date` are no longer wrapped in a `.status-meta` container, and — unlike the date — the badge isn't even a descendant of `.status-header` any more. `renderStatusCard()` appends `.new-badge` as the very first child of `.status-card` itself, before the reblog banner or the header, specifically so it anchors to `.status-card` (`position: relative`) rather than `.status-header`: `top: 16px; right: 16px`, matching the card's own padding, so it sits in the exact same spot for every post regardless of whether a `.reblog-banner` pushes the header down underneath it — a reblog and a plain post both get the badge in the identical corner. `.status-date`, by contrast, stays inside `.status-header` (`position: relative`, a fixed ~48px tall row since `.status-author`'s two lines never wrap) and anchors to *that* instead, at `bottom: 0; right: 0` — lining up with the username row below it, wherever the header happens to sit. Anchoring the date to `.status-header` rather than `.status-card` matters — the header's height is stable regardless of post body length, while the card's isn't, so `bottom: 0` on the date would be meaningless anchored to the card. This whole scheme replaced an earlier design where the badge/date were real flex children stacked together in a `.status-meta` column (working, but needing a different empirically-tuned `margin-top` per breakpoint to fake the date's alignment with the username row whenever the badge wasn't present — fragile, since any font-size/line-height change nearby could silently throw it off — and, since badge and date shared one flex parent, unable to give the badge a card-relative fixed point independent of the header's own position). Because both are taken out of flow entirely, `.status-author` (the only remaining flex sibling besides the avatar) would otherwise expand to the full row width and run its truncated text underneath them — so `.status-header` carries a permanent `padding-right` (110px desktop, 90px mobile) sized to fit the corner column, unconditionally rather than only when `is-new` like before, since the date is now always present as an overlay. `timelineFeed`'s `renderCard` computes `isNew` from the *top-level* `status.created_at` — not `original.created_at`, since for a reblog the top-level date is when it entered the timeline, which is what "new" should track — compared against `timelineLastSeenBefore`. On a list's very first-ever view there is no stored marker, so nothing is flagged as new (avoids highlighting the whole history). The marker only advances on a fresh load, so posts stay marked "new" for the rest of that same viewing session even as lazy-loading fetches older pages.

**Rendering & sanitization:** `renderStatusCard(status, isNew, showActions, showAuthor)` builds each post's DOM manually (no templating library) — all three flags are supplied by whichever feed engine's `renderCard` calls it (Timeline passes a freshly-computed `isNew`, `showActions: true`, `showAuthor: true`; Profile always passes `false, false, false` — see **Profile** above and **New-post highlighting** below). `showActions: false` skips building the Favourite and Reblog `<button>`s entirely; the "View post" `<a>` is unconditional regardless of `showActions`, so it's the one action a `showActions: false` card keeps. `showAuthor: false` skips the avatar/display-name/handle block entirely and gives `.status-header` a second class, `status-header-date-only`, so only the date renders — that variant can't just reuse `.status-date`'s usual `position: absolute` corner anchor as-is, since that anchor is specifically sized/placed to coexist with the avatar+name row and the "New" badge (via `.status-header`'s `padding-right`), neither of which exist on a `showAuthor: false` card; `.status-header.status-header-date-only` (`style.css`) resets `padding-right` to `0`, right-aligns the date with `justify-content: flex-end` on the now-single-child flex row, and switches `.status-date` itself back to normal (`position: static`) flow so the header's height comes from the date text's own line-height instead of collapsing to nothing (an absolutely-positioned lone child contributes no height to its flex parent). That selector's two classes (specificity 0,2,0) deliberately beat both the desktop and the mobile `.status-header` `padding-right` rules unconditionally, rather than relying on `style.css`'s source-order convention for the mobile override (see **Responsive layout** below) to also happen to still win here. Media (`buildMediaElement()`) uses `media_attachments[].url` (the full-resolution file) rather than `preview_url` (a thumbnail Mastodon caps around ~400px on the long edge) — given the app's whole purpose is showing photos, the preview would be a visible quality regression; `preview_url` is kept only as a fallback if `url` is ever missing, and images are marked `loading="lazy"` since full-resolution files are heavier. It is always rendered before the body text — including inside content-warning posts, where both live inside the `<details>` collapse. Images/videos are shown at their original aspect ratio (`height: auto`, no cropping). Status `content` from the API is HTML and is passed through `sanitizeStatusHtml()`, a hand-rolled allowlist sanitizer (permitted tags in `ALLOWED_TAGS`; all attributes stripped except a safety-checked `href` on `<a>`, which also gets `rel`/`target` forced) rather than trusting Mastodon's server-side sanitization outright. `href` values are validated with `isHttpUrl()` (imported from `pure.mjs`) — an allowlist requiring the resolved URL's scheme to be `http:`/`https:` — rather than a denylist of known-bad schemes like `javascript:`. `isHttpUrl()`'s second parameter (`base`) defaults to `window.location.href` in the browser and to `undefined` in Node (detected via `typeof window`), so every existing call site in `app.js` behaves exactly as before without passing it explicitly, while `pure.test.mjs` can still call it with plain absolute URLs. Before attributes are stripped, the sanitizer detects Mastodon's hashtag markup (`class="...hashtag..."` or `rel="tag"`) and re-tags the link with a `tag-link` class so hashtags can be styled smaller/muted in CSS separately from regular links. The `isHttpUrl()` guard is also reused outside the sanitizer, for two links that both only render when the relevant field is present and passes the check (falling back to plain, non-linked text/no button otherwise): the author's `username` element as an `<a href="original.account.url">` (the author's **profile**, not the post — don't confuse the two `url` fields, `account.url` vs the status's own `url`), and a "View post" link/button (`.view-original-btn`) in `.status-actions`, using `original.url` (the status's own permalink, on its origin instance), placed after the favourite/reblog buttons.

**Custom emoji shortcodes:** Mastodon never resolves a `:shortcode:` itself — `content`, `spoiler_text`, and `display_name` all carry the literal shortcode text, alongside a separate `emojis` array (on the Status for the first two, on the Account for the third) mapping each shortcode to an image `url`. `renderEmojiText(text, emojis)` (in `pure.mjs`, DOM-free and covered by `pure.test.mjs`) handles the plain-text cases — `display_name` (status header, reblog banner, list-members preview) and `spoiler_text` — by escaping the text first and then replacing each shortcode still present in the *escaped* string with an `<img class="emoji">`, guarded by the same `isHttpUrl()` allowlist as every other external URL in the app; a shortcode with no matching (or unsafe) emoji entry is left as plain escaped text. `content` is HTML, not plain text, so it can't go through `renderEmojiText()` directly — instead `sanitizeStatusHtml()` takes an `emojis` param and calls `renderEmojiText()` per *text node* during its existing DOM walk (`replaceEmojiShortcodes()`), replacing a matching text node with the parsed result's child nodes via `textNode.replaceWith(...)`. This runs after the tag/attribute allowlist check for that DOM level, so the `<img>` tags it introduces are never subject to (or stripped by) `ALLOWED_TAGS`, which deliberately doesn't include `IMG` — a raw `<img>` tag actually present in a status's `content` is still stripped like any other disallowed tag, only ones `renderEmojiText()` itself constructs from a validated emoji URL survive. `img.emoji` is styled at a fixed `1.2em` square so it renders inline at roughly text size regardless of the source image's actual dimensions. `escapeHtml()` itself also moved into `pure.mjs` (both to build `renderEmojiText()` on it and to let `pure.test.mjs` cover it directly); `app.js` keeps a local `escapeAttr` as an alias, unchanged at every call site.

**Security headers:** since GitHub Pages serves this app with no custom HTTP headers, `index.html` sets a `Content-Security-Policy` via `<meta http-equiv>` (`script-src 'self'`, `object-src 'none'`, `form-action 'none'`, etc.) as defense-in-depth. Note `<meta>` CSP cannot carry a `frame-ancestors` directive (browsers ignore it there), so this does not protect against clickjacking — that would require a real HTTP header from something fronting GitHub Pages.

**Pull to refresh:** `#pull-refresh` is a normally-zero-height flow element (not `position:fixed`) sitting right above `#timeline-container`; growing its inline `style.height` on `touchmove` naturally pushes the feed down, mimicking native pull-to-refresh. It only arms when `el.timelineView` is visible and `window.scrollY === 0` at `touchstart` (so it never fires mid-scroll or from other views), and calls `preventDefault()` on `touchmove` (registered `{ passive: false }`) to stop the browser's own rubber-banding while dragging — `body` also sets `overscroll-behavior-y: contain` so the native overscroll/refresh gesture doesn't fight with this one. Crossing `PULL_THRESHOLD` (70px, from a raw drag distance damped by ×0.5, capped at `PULL_MAX`) flips the `.ready` class (rotates the arrow, swaps the label) and, on release past that threshold, calls `timelineFeed.load(false)` — the same call a fresh list selection uses — this exists specifically because standalone/home-screen mode on iOS and Android has no built-in reload gesture the way a regular browser tab does. `touchstart`'s arming check no longer guards on a "busy" flag — since `load()` calls now go through the per-instance queue described in **Lazy loading** above, correctness doesn't depend on blocking the gesture from starting; `await timelineFeed.load(false)` here simply stays pending for as long as it actually takes (including any wait behind an unrelated auto-load already in flight), so "Refreshing…" is only ever shown for a genuinely in-progress refresh, never a false-positive flash. This gesture is Timeline-only by construction, not by an extra guard: it's gated solely on `el.timelineView` being visible, and `showView()` makes Timeline/Profile mutually exclusive, so a swipe while Profile is showing is already correctly a no-op.

**Lightbox:** clicking (or, since the feed's `<img>`s are `tabindex="0" role="button"`, focusing + pressing Enter/Space on) a photo (`buildMediaElement()`'s `img` elements only, not video/gifv) calls `openLightbox(photos, index, triggerEl)`, where `photos` is that post's *own* image attachments only (built once per `buildMediaElement()` call, filtered from `media_attachments` before the per-attachment loop, mapped to `{ src, alt }`) and `index` is that photo's position within it — not a single `(src, alt)` pair, specifically so the lightbox knows what else is in the same post's gallery. It reuses the same full-resolution URLs already used in the feed and just displays the current one larger in a single fixed-position `#lightbox` overlay (`role="dialog" aria-modal="true"` in `index.html`, shown/hidden via the shared `.hidden` class). There's exactly one lightbox `<img>` in the DOM, repointed via `showLightboxPhoto(index)` on open and on every navigation — not one per photo. On a post with more than one photo, the lightbox can move between them: `ArrowLeft`/`ArrowRight` (guarded to only act while the lightbox is actually open, unlike `Escape` which is harmless to call unconditionally), and a horizontal touch swipe past `LIGHTBOX_SWIPE_THRESHOLD` (50px) — `touchmove` only calls `preventDefault()` once the drag is clearly more horizontal than vertical, so a vertical swipe/scroll isn't hijacked, and `touchend` also calls it when a swipe was actually acted on, which suppresses the synthetic `click` event that would otherwise immediately close the lightbox right after swiping. Both directions clamp at the gallery's ends rather than wrapping around. Opening moves focus to `#lightbox-close` (a visible × button); closing — via that button, a click anywhere on the overlay including the image, or Escape (all wired once at startup rather than per-photo) — returns focus to whichever photo triggered it (`lightboxTrigger`, captured at open time).

**Favourite/reblog:** `toggleFavourite()`/`toggleReblog()` call the respective `/favourite`/`unfavourite` and `/reblog`/`unreblog` endpoints and update the button label/state from the API response rather than optimistically.
