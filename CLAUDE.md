# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Mastofoto is a static, single-user web app (`index.html` + `style.css` + `app.js`, plus `pure.mjs` for a handful of DOM-free functions) that lets someone log into a Mastodon instance, pick one Mastodon list, and view only the posts in that list that contain photos (image attachments), with the ability to favourite and reblog them. It runs entirely client-side against the Mastodon REST API — there is no backend, no build step, and no database. All persisted state lives in the browser's `localStorage`. The page has no runtime dependencies besides the Mastodon instance itself; the header wordmark is a pre-rendered static image (`assets/logo.png`) rather than a webfont, so nothing is fetched from a font CDN at runtime. All UI copy (labels, buttons, error messages) is in English (`<html lang="en">`) — the app was originally built with Italian strings, fully translated later, so don't reintroduce Italian text when adding new user-facing strings.

## Development

There is no build step and no runtime dependencies. `package.json` exists solely to declare `"type": "module"` (so `app.js`'s `import` from `pure.mjs` resolves the same way for Node — `node --check`/`node --test` — as it does in the browser via `<script type="module">`); it has no dependencies and nothing to `npm install`.

- Opening `index.html` directly as a `file://` page does **not** work for testing login — the OAuth redirect flow needs a real `http(s)://` origin (see Architecture below), and browsers also block ES module imports (`<script type="module">`) from `file://` regardless. Serve the directory instead, e.g. `python3 -m http.server`, and use `http://localhost:8000/`.
- **Don't use VS Code's "Live Preview" extension** to test this app in an external browser: it gates its static files behind an internal auth cookie/token that's only present when the page is opened *through VS Code itself*. Loading the same `http://localhost:3000/...` URL directly in a real browser tab gets `app.js` a `401 Unauthorized` (silently breaking everything, since no JS ever runs — this looks like "login doesn't work" but is really "nothing runs"), and its injected live-reload script tries to open a `ws://` connection that this app's CSP correctly blocks (`connect-src https:` — harmless, just means Live Preview's auto-refresh won't work, not a real problem). Plain `python3 -m http.server` has neither issue.
- After editing `app.js` or `pure.mjs`, check they parse with `node --check <file>`.
- Run the test suite with `node --test` (or `npm test`) — it covers the pure functions in `pure.mjs` (`isHttpUrl`, `hasPhoto`, `parseNextMaxId`) via `pure.test.mjs`, using Node's built-in test runner, no added dependency. `sanitizeStatusHtml()` in `app.js` is **not** covered here — it needs `DOMParser`, which Node doesn't provide without adding a dependency (e.g. jsdom), so it stays manually reviewed rather than unit-tested. When touching `pure.mjs`, keep behavior identical between the browser and Node call paths — see `isHttpUrl`'s `base` parameter below.
- End-to-end testing (OAuth login, list fetching, favourite/reblog) requires a real Mastodon account/instance and cannot be simulated locally.

**Branches:** there are three. `dev` is where new work happens (in-progress features/fixes land here first, not directly on `main`). `main` is the clean, open-source branch (what this repo looks like to the world / forks) — merge `dev` into it once work is settled. `production` is what GitHub Pages actually serves; it's `main` plus a small personal layer (a `rel="me"` link back to the site owner's Mastodon profile, and an Umami analytics script tag) that must never be merged back into `main` or `dev`. The flow is `dev` → `main` → `production`, each step a manual merge when ready — nothing here is automatic or CI-driven:
```
git checkout main && git merge dev && git push origin main
git checkout production && git merge main && git push origin production
```
The personal-layer commits on `production` stay on top and shouldn't conflict since they only touch a couple of lines in `index.html`'s `<head>` and its CSP `script-src`.

**Releasing a version:** every release (whenever the user asks to "release version X.Y.Z") must, in addition to the usual changelog-entry-plus-git-tag flow: (1) update the `APP_VERSION` constant near the top of `app.js` to the new version, which is what's displayed on the "About Mastofoto" page (`#app-version`, set once at startup) — do this even for a patch release with no other user-visible change, since the version display existing at all is the point.

## Architecture

All logic lives in `app.js` as a single IIFE with a small `state` object (`instance`, `token`, `currentListId`, `nextMaxId`) and an `el` object caching DOM references. Views are plain `<section>`s in `index.html` shown/hidden via a `.hidden` CSS class (`login-view`, `list-setup-view`, `timeline-view`, `info-view`) — there is no router or framework. `info-view` is a static "About Mastofoto" page (feature list, a "Security & data" summary written for end users — keep it in sync in plain language whenever the actual security/storage behavior changes elsewhere in this file, and link to the GitHub repo); its own "Home Page" link (`href="."`, same pattern as `list-setup-view`'s) is the only way back, since the app deliberately doesn't track "previous view" state — the info button's click handler just hides `timelineView`/`listSetupView` and shows `infoView`.

**Auth flow (OAuth2, standard redirect):**
1. `REDIRECT_URI` is computed once at load time as `window.location.origin + window.location.pathname` — it always points back at wherever the page is currently being served from, so no URL is hardcoded and the flow works unmodified on GitHub Pages, a custom domain, or `http://localhost` during local testing. This is also why a `file://` origin doesn't work: Mastodon requires a real, matching redirect URI.
2. User enters an instance domain. If no app credentials exist yet for that instance, `registerApp()` calls `POST /api/v1/apps` to dynamically register the app (with `REDIRECT_URI`) and stores `client_id`/`client_secret`; the instance name and a random `state` (`crypto.randomUUID()`) are stashed in `localStorage` under `PENDING_INSTANCE_KEY`/`PENDING_STATE_KEY`, `state` is included in the authorize URL, and the whole page navigates to the instance's `/oauth/authorize` URL (`window.location.href =`, not a popup/new tab).
3. Mastodon redirects the browser back to `REDIRECT_URI` with `?code=...&state=...` (or `?error=...` if the user declines). On load, `init()` reads those query params, calls `completeAuthorization(code, returnedState)` — which requires `returnedState` to exactly match the stored `PENDING_STATE_KEY` (both pending keys are consumed/cleared regardless of outcome, so this check only ever accepts a code that was in flight from a login this same browser just started, closing a login-CSRF gap), then looks up the pending instance and its stored `client_id`/`client_secret`, exchanges the code via `exchangeCodeForToken()` (`POST /oauth/token`), and starts the session. The query string is stripped with `history.replaceState()` before any of this so the code/state aren't left in the URL/history.
4. Scope requested is `read write:favourites write:statuses` — enough for reading lists/timelines and for favouriting/reblogging, deliberately excluding general posting.

All credentials (`clientId`, `clientSecret`, `accessToken`, `listId`) are namespaced per-instance in `localStorage` via `storageKey(instance, name)` (`mastofoto:<instance>:<name>`), plus a `mastofoto:lastInstance` pointer used to auto-resume a session on load. Because there is no backend, the client secret is necessarily exposed in the browser — acceptable for this single-user use case but worth remembering if the scope of the app ever changes. Note that switching hosting origins (e.g. testing on `localhost` after having registered the app on the production URL) invalidates the cached `client_id`/`client_secret` for that instance, since Mastodon validates the redirect URI against what the app was registered with — clear that instance's localStorage entries (or log out) if authorization starts failing after a hosting change.

**Service worker:** `sw.js` (repo root, so its scope covers the whole app regardless of hosting path) caches the static shell only — `index.html`, `style.css`, `app.js`, `manifest.json`, the logo/favicon — never API responses (the fetch handler bails out on any cross-origin request, which covers every Mastodon API call automatically since those always hit `https://${instance}`). It's **network-first, cache-as-fallback**, not cache-first: every same-origin GET tries the network first and updates the cache on success, only falling back to the cache when the network fails. This was a deliberate choice given how often this project ships releases — a naive cache-first strategy would need its `CACHE_NAME` bumped in lockstep with every release (like `APP_VERSION`) to avoid serving a stale app indefinitely; network-first self-heals instead, so `CACHE_NAME` only needs bumping if the shell file list itself changes. Registered from `app.js` behind an `if ('serviceWorker' in navigator)` check, after `window.load`.

**Blurhash placeholders:** `decodeBlurhash()`/`blurhashToDataUrl()` in `app.js` are a from-scratch reimplementation of the public blurhash algorithm (https://blurha.sh) — deliberately not the npm package, to keep the app dependency-free. `buildMediaElement()` decodes each image's `att.blurhash` into a small (32×32) canvas, and sets the result as the `<img>`'s CSS `background-image` (cleared on `load`) so a blurred preview shows while the full-resolution file downloads. This needed `data:` added to the CSP's `img-src` (still no change to `script-src`/`style-src`, so it doesn't loosen anything script-execution-relevant). The `<img>` also gets `width`/`height` HTML attributes from `att.meta.original` (falling back to `att.meta.small`) — set from the image's own true dimensions, not a cropped/different ratio, so this only reserves layout space and lets the blurhash placeholder actually be visible before load; it doesn't reintroduce cropping (still no `object-fit`).

**Logo & favicon assets:** `assets/logo.png` is a pre-rendered transparent PNG of the word "Mastofoto" set in the Google Font "Pacifico" — it exists specifically so the page never has to load a webfont at runtime. `assets/favicon.png`/`assets/favicon.ico` are the same treatment applied to just the letter "M", cropped/centered to fill the icon square. Both were generated with Pillow (`ImageFont.truetype` + `ImageDraw.text`, measuring the glyph's `textbbox` to scale and center it before rendering) from the actual Pacifico TTF (fetched from `fonts.gstatic.com`), not with a browser. To regenerate either (e.g. a different color/size), re-run that kind of script rather than trying to reintroduce a `<link>` to Google Fonts. `assets/favicon.png` is also reused as the mobile home-screen icon, referenced both by an `apple-touch-icon` `<link>` and by `manifest.json`'s single 512×512 `icons` entry (no separate asset needed since browsers scale it down); regenerate that same file if the icon ever changes and both references stay valid.

**Theme (light/dark):** every color in `style.css` is a CSS custom property, defined on `:root` (light, the default) and re-declared under `:root[data-theme="dark"]` — no bare hex/rgba should appear outside those two blocks; a new color needs a token added to both, even if the value is identical in both themes (e.g. `--btn-primary-bg`, `--accent-contrast`, `--overlay-bg` don't change between themes, but stay tokenized for consistency and so every color has exactly one place to look it up). The background asked for specifically was `#191d20`. `--shadow` is the one value that *does* differ non-trivially — `.card`/`.status-card`'s box-shadow is bumped to a higher opacity in dark mode since a shadow the same strength as light mode barely reads against a dark page. `app.js` computes the effective theme once at startup (`getPreferredTheme()`): an explicit choice in `localStorage` (`mastofoto:theme`) wins, otherwise it falls back to `prefers-color-scheme`. `applyTheme()` sets the `data-theme` attribute on `<html>` and also updates the `<meta name="theme-color">` tag so the mobile/PWA chrome matches. The picker lives in Settings (`#theme-select`) as a plain `<select>`, seeded with the effective theme on load and persisting explicitly on `change` — there's no "system/auto" option once a user has picked one, and no listener for the OS preference changing while the app is open (out of scope; re-opening the app or re-toggling covers it).

**Brand blue vs. accessible blue:** `#2b90d9` (the literal brand color baked into `assets/logo.png`/`assets/favicon.png` and `manifest.json`'s `theme-color`) measures only ~3.45:1 against white, short of the 4.5:1 normal-text requirement — so it is used **only** for those non-text, decorative contexts and is deliberately **not** a CSS variable in `style.css`. Every place that needs actual contrast uses one of two separate, accessible tokens instead: `--btn-primary-bg` (`#1c69a0`, identical in both themes — button-fill contrast against its own white label doesn't depend on the page theme, since the button *is* the immediate background) for solid buttons/`.new-badge`/the active favourite-reblog state, and `--link` (`#1a6699` light / `#5aa9e6` dark — a link's background *is* the page surface, which does change per theme, so this one can't share a single value like `--btn-primary-bg` does) for inline text links and the photo focus-visible outline. Don't reintroduce `#2b90d9` (or a `var(--accent)`-style alias for it) into any text- or button-fill rule — that's exactly the contrast failure this split fixed.

**Accessibility:** contrast has been checked by computing actual WCAG ratios (not eyeballed) for every token pair — `--text-tertiary`, `--border-strong`, `--btn-primary-bg`, and `--link` were all measured failures in the original palette (before the brand/link split above) and are now tuned to pass (≥4.5:1 for text, ≥3:1 for UI component borders) in both themes; re-verify with the relative-luminance formula (not intuition) if any of these tokens change again. The page has exactly one `<h1>` (`.sr-only`, "Mastofoto", in the header, present across all views since the header itself never hides) with each view's own heading correctly nested under it as `<h2>`/`<h3>`/`<h4>` — don't add a second `<h1>` if a view's title ever needs promoting for some other reason.

**Responsive layout:** all mobile overrides live in a single `@media (max-width: 480px)` block at the very end of `style.css`, rather than scattered near each base rule — this matters because a media query has the same specificity as the plain selector it targets, so with equal specificity the rule *later in the file* wins regardless of the media query; keeping the block at the end guarantees every override comes after its unconditional base rule. Notable overrides: `#session-info`'s "Settings"/"Log out" buttons wrap their label in `<span class="btn-icon">`/`<span class="btn-label">`, and the mobile rule hides `.btn-label` and turns the button into a circular icon-only button matching `.icon-btn` (the info button's style); `.status-header` gets `flex-wrap` so `.status-date` (`flex-basis: 100%`) wraps onto its own line below the author info instead of sharing the top row, indented with `padding-left` (not `margin-left`) — margin sits outside a `flex-basis: 100%` box and would push the whole row past the viewport edge, forcing page-wide horizontal scroll, while padding is absorbed into that 100% under the global `box-sizing: border-box`. Don't reintroduce a second `@media (max-width: 480px)` block elsewhere in the file — add new mobile rules to the existing one at the bottom.

**List configuration:** the app intentionally supports exactly one active list at a time (not a multi-list browser). `showListSetup()` fetches `/api/v1/lists` and lets the user pick one; the choice is persisted as `listId` per-instance and reused on future logins. The "Settings" button (`change-list-btn` — the id is unchanged from before the rename, still just opens `#list-setup-view`) re-opens the same screen to switch lists later; that screen also holds the theme picker (see **Theme** below), unrelated to any single Mastodon list/instance. That screen also previews the selected list's membership via `loadListMembers()` (`GET /api/v1/lists/:id/accounts?limit=80` — a single page, no pagination, since these are meant to be small curated lists), sorted alphabetically by `display_name || username` with `localeCompare(..., { sensitivity: 'base' })`; it re-fetches on the select's `change` event and once right after the dropdown is first populated in `showListSetup()`. The list has no `max-height`/scroll of its own — it renders in full and lets the page scroll. Each member's name is linked to `account.url` (profile), same `isHttpUrl()`-guarded fallback-to-plain-text pattern as the post author links.

**Timeline & photo filtering:** `loadTimeline()` fetches `/api/v1/timelines/list/:id`, paginates using the `Link: rel="next"` header (falling back to the last returned status id via `parseNextMaxId()`), and then filters results client-side with `hasPhoto()` — only statuses (or reblogs) with at least one `media_attachments` entry of type `image` are rendered. This filtering happens after pagination, so "Load more" may need multiple clicks to surface new photo posts if a page has none.

**New-post highlighting:** on every non-append `loadTimeline()` call (i.e. a fresh list load, not "Load more"), `state.lastSeenBefore` is set from the previous value of a per-list `localStorage` marker (`lastSeenKey(listId)` → `lastSeen:<listId>`), *before* that marker is overwritten with the newest fetched photo status's `created_at`. `renderStatusCard()` then flags a card `is-new` (only used for the `"New"` badge shown next to the timestamp — the card itself is no longer tinted) — `.status-meta` stacks the badge above `.status-date` in a right-aligned column on desktop (lining up with the author's name/handle above), but on mobile `.new-badge` switches to `position: absolute` pinned to `.status-card`'s top-right corner (which is why `.status-card` has `position: relative`) instead of following the date onto its wrapped line — when the *top-level* `status.created_at` — not `original.created_at`, since for a reblog the top-level date is when it entered the timeline, which is what "new" should track — is newer than `state.lastSeenBefore`. On a list's very first-ever view there is no stored marker, so nothing is flagged as new (avoids highlighting the whole history). The marker only advances on a fresh load, so posts stay marked "new" for the rest of that same viewing session even as "Load more" fetches older pages.

**Rendering & sanitization:** `renderStatusCard()` builds each post's DOM manually (no templating library). Media (`buildMediaElement()`) uses `media_attachments[].url` (the full-resolution file) rather than `preview_url` (a thumbnail Mastodon caps around ~400px on the long edge) — given the app's whole purpose is showing photos, the preview would be a visible quality regression; `preview_url` is kept only as a fallback if `url` is ever missing, and images are marked `loading="lazy"` since full-resolution files are heavier. It is always rendered before the body text — including inside content-warning posts, where both live inside the `<details>` collapse. Images/videos are shown at their original aspect ratio (`height: auto`, no cropping). Status `content` from the API is HTML and is passed through `sanitizeStatusHtml()`, a hand-rolled allowlist sanitizer (permitted tags in `ALLOWED_TAGS`; all attributes stripped except a safety-checked `href` on `<a>`, which also gets `rel`/`target` forced) rather than trusting Mastodon's server-side sanitization outright. `href` values are validated with `isHttpUrl()` (imported from `pure.mjs`) — an allowlist requiring the resolved URL's scheme to be `http:`/`https:` — rather than a denylist of known-bad schemes like `javascript:`. `isHttpUrl()`'s second parameter (`base`) defaults to `window.location.href` in the browser and to `undefined` in Node (detected via `typeof window`), so every existing call site in `app.js` behaves exactly as before without passing it explicitly, while `pure.test.mjs` can still call it with plain absolute URLs. Before attributes are stripped, the sanitizer detects Mastodon's hashtag markup (`class="...hashtag..."` or `rel="tag"`) and re-tags the link with a `tag-link` class so hashtags can be styled smaller/muted in CSS separately from regular links. The `isHttpUrl()` guard is also reused outside the sanitizer, for two links that both only render when the relevant field is present and passes the check (falling back to plain, non-linked text/no button otherwise): the author's `username` element as an `<a href="original.account.url">` (the author's **profile**, not the post — don't confuse the two `url` fields, `account.url` vs the status's own `url`), and a "View post" link/button (`.view-original-btn`) in `.status-actions`, using `original.url` (the status's own permalink, on its origin instance), placed after the favourite/reblog buttons.

**Security headers:** since GitHub Pages serves this app with no custom HTTP headers, `index.html` sets a `Content-Security-Policy` via `<meta http-equiv>` (`script-src 'self'`, `object-src 'none'`, `form-action 'none'`, etc.) as defense-in-depth. Note `<meta>` CSP cannot carry a `frame-ancestors` directive (browsers ignore it there), so this does not protect against clickjacking — that would require a real HTTP header from something fronting GitHub Pages.

**Pull to refresh:** `#pull-refresh` is a normally-zero-height flow element (not `position:fixed`) sitting right above `#timeline-container`; growing its inline `style.height` on `touchmove` naturally pushes the feed down, mimicking native pull-to-refresh. It only arms when `el.timelineView` is visible and `window.scrollY === 0` at `touchstart` (so it never fires mid-scroll or from other views), and calls `preventDefault()` on `touchmove` (registered `{ passive: false }`) to stop the browser's own rubber-banding while dragging — `body` also sets `overscroll-behavior-y: contain` so the native overscroll/refresh gesture doesn't fight with this one. Crossing `PULL_THRESHOLD` (70px, from a raw drag distance damped by ×0.5, capped at `PULL_MAX`) flips the `.ready` class (rotates the arrow, swaps the label) and, on release past that threshold, calls the same `loadTimeline(false)` used by a fresh list load — this exists specifically because standalone/home-screen mode on iOS and Android has no built-in reload gesture the way a regular browser tab does.

**Lightbox:** clicking (or, since the feed's `<img>`s are `tabindex="0" role="button"`, focusing + pressing Enter/Space on) a photo (`buildMediaElement()`'s `img` elements only, not video/gifv) calls `openLightbox(fullSrc, alt, triggerEl)`, which reuses the same full-resolution URL already used in the feed and just displays it larger in a single fixed-position `#lightbox` overlay (`role="dialog" aria-modal="true"` in `index.html`, shown/hidden via the shared `.hidden` class). There's exactly one lightbox `<img>` in the DOM, repointed on each open — not one per photo. Opening moves focus to `#lightbox-close` (a visible × button); closing — via that button, a click anywhere on the overlay including the image, or Escape (all wired once at startup rather than per-photo) — returns focus to whichever photo triggered it (`lightboxTrigger`, captured at open time).

**Favourite/reblog:** `toggleFavourite()`/`toggleReblog()` call the respective `/favourite`/`unfavourite` and `/reblog`/`unreblog` endpoints and update the button label/state from the API response rather than optimistically.
