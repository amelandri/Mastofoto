# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Mastofoto is a static, single-user web app (`index.html` + `style.css` + `app.js`, plus `pure.mjs` for a handful of DOM-free functions) that lets someone log into a Mastodon instance, pick one Mastodon list (or their Home timeline), and view only the posts there that contain photos (image attachments), with the ability to favourite and reblog them. It runs entirely client-side against the Mastodon REST API — there is no backend, no build step, and no database. All persisted state lives in the browser's `localStorage`. The page has no runtime dependencies besides the Mastodon instance itself; the header wordmark is a pre-rendered static image (`assets/logo.png`) rather than a webfont, so nothing is fetched from a font CDN at runtime. All UI copy (labels, buttons, error messages) is in English (`<html lang="en">`) — the app was originally built with Italian strings, fully translated later, so don't reintroduce Italian text when adding new user-facing strings.

## Development

There is no build step and no runtime dependencies. `package.json` exists solely to declare `"type": "module"` (so `app.js`'s `import` from `pure.mjs` resolves the same way for Node — `node --check`/`node --test` — as it does in the browser via `<script type="module">`); it has no dependencies and nothing to `npm install`.

- Opening `index.html` directly as a `file://` page does **not** work for testing login — the OAuth redirect flow needs a real `http(s)://` origin (see Architecture below), and browsers also block ES module imports (`<script type="module">`) from `file://` regardless. Serve the directory instead, e.g. `python3 -m http.server`, and use `http://localhost:8000/`.
- **Don't use VS Code's "Live Preview" extension** to test this app in an external browser: it gates its static files behind an internal auth cookie/token that's only present when the page is opened *through VS Code itself*. Loading the same `http://localhost:3000/...` URL directly in a real browser tab gets `app.js` a `401 Unauthorized` (silently breaking everything, since no JS ever runs — this looks like "login doesn't work" but is really "nothing runs"), and its injected live-reload script tries to open a `ws://` connection that this app's CSP correctly blocks (`connect-src https:` — harmless, just means Live Preview's auto-refresh won't work, not a real problem). Plain `python3 -m http.server` has neither issue.
- After editing `app.js` or `pure.mjs`, check they parse with `node --check <file>`.
- Run the test suite with `node --test` (or `npm test`) — it covers the pure functions in `pure.mjs` (`isHttpUrl`, `hasPhoto`, `parseNextMaxId`) via `pure.test.mjs`, using Node's built-in test runner, no added dependency. `sanitizeStatusHtml()` in `app.js` is **not** covered here — it needs `DOMParser`, which Node doesn't provide without adding a dependency (e.g. jsdom), so it stays manually reviewed rather than unit-tested. When touching `pure.mjs`, keep behavior identical between the browser and Node call paths — see `isHttpUrl`'s `base` parameter below.
- End-to-end testing (OAuth login, list fetching, favourite/reblog) requires a real Mastodon account/instance and cannot be simulated locally.
- Testing from a real phone against the dev server means browsing to the Mac's LAN IP (e.g. `http://192.168.0.15:8000`) instead of `localhost` — that origin is **not** a secure context (only HTTPS and `http://localhost`/`127.0.0.1` count), so any Web Crypto API gated behind one becomes unavailable there even though the exact same code works from `http://localhost:8000`. Login's `state` generation already tolerates this (see the `randomUUID()` helper in Architecture below). `navigator.serviceWorker.register()` has the same secure-context requirement and is *not* worked around the same way — its existing `.catch(() => {})` just means it silently no-ops on a plain LAN IP instead of erroring, which is fine since offline caching is a nice-to-have, not something login depends on.

**Branches:** there are three. `dev` is where new work happens (in-progress features/fixes land here first, not directly on `main`). `main` is the clean, open-source branch (what this repo looks like to the world / forks) — merge `dev` into it once work is settled. `production` is what GitHub Pages actually serves; it's `main` plus a small personal layer (a `rel="me"` link back to the site owner's Mastodon profile, an Umami analytics script tag, and a one-line disclosure on the login page — right after `.app-disclosure`, styled with the plain `.hint` class rather than `.app-disclosure` itself so it doesn't add a second divider — mentioning that this specific deployment runs that analytics) that must never be merged back into `main` or `dev`. The flow is `dev` → `main` → `production`, each step a manual merge when ready — nothing here is automatic or CI-driven:
```
git checkout main && git merge dev && git push origin main
git checkout production && git merge main && git push origin production
```
The personal-layer commits on `production` stay on top and shouldn't conflict since they only touch a couple of lines in `index.html`'s `<head>` and its CSP `script-src`.

**Releasing a version:** every release (whenever the user asks to "release version X.Y.Z") must, in addition to the usual changelog-entry-plus-git-tag flow: (1) update the `APP_VERSION` constant near the top of `app.js` to the new version, which is what's displayed on the "About Mastofoto" page (`#app-version`, set once at startup) — do this even for a patch release with no other user-visible change, since the version display existing at all is the point.

## Architecture

All logic lives in `app.js` as a single IIFE with a small `state` object (`instance`, `token`, `currentListId`, `nextMaxId`) and an `el` object caching DOM references. Views are plain `<section>`s in `index.html` (`login-view`, `list-setup-view`, `timeline-view`, `info-view`), all four marked `class="hidden"` in the static markup — there is no router or framework, and no view is visible-by-default at first paint. Exactly one is visible at a time, enforced by a single `showView(view)` helper (`VIEWS.forEach(hide); show(view);`) that every handler calls instead of hiding/showing sections by hand — `init()`'s bootstrap explicitly calls `showView(el.loginView)` in every branch where it isn't resuming a session (no stored token, an auth error, a failed code exchange) rather than relying on the HTML to show login by default; `login-view` used to lack the `hidden` class for exactly that "default" reason, but since `startSession()` awaits a network round-trip (`verify_credentials`) before switching to the timeline, that made the login page visibly flash for a moment on every reload of an already-logged-in session — that hand-rolled approach is what caused a real bug (logging out from the Info page left it visible behind the login form, because the logout handler's manual hide-list didn't include `infoView`); always add a new view to the `VIEWS` array rather than hiding/showing it directly. `#session-info` (the header's action buttons) is a separate concern from the four views, not part of `showView()` — and unlike the views, its three buttons aren't toggled as a group. `change-list-btn` ("Settings") and `logout-btn` are individually shown/hidden based on login state (they need a session to mean anything), but `info-btn` has no `hidden` class anywhere and is never toggled — it's always visible, logged in or not, since `#app-header` itself is never hidden. `info-view` is a static "About Mastofoto" page (feature list, an "Accessibility" summary, a "Security & data" summary written for end users — keep both in sync in plain language whenever the actual behavior changes elsewhere in this file, and link to the GitHub repo); its own "Home Page" button is the only way back. There are two ways in, both wiring to the same `showView(el.infoView)` call: the always-visible header `info-btn`, and `login-info-btn`, a link inside the login page's disclosure text (redundant with the header button now that it's unconditionally visible, but kept since it reads naturally as part of that sentence).

**"Home Page" navigation:** `list-setup-view` and `info-view` each have a `.home-link` element (`list-setup-home-btn`/`info-home-btn`) that used to be a plain `<a href=".">` — that caused a full page reload just to get back to a view that was already loaded in memory (re-fetching `app.js`, re-running `verify_credentials`, and re-fetching the timeline from scratch via `selectList()`), a visible lag compared to the instant, in-memory `showView()` call every other navigation in the app already uses (e.g. the header's Settings/Info buttons). Both are now `<button>`s wired to a shared `goHome()` (right next to `showView()`), which picks the destination from current session state rather than tracking "previous view" history: no session → `loginView`; logged in with a list already loaded → `timelineView` (reusing whatever is already rendered, no refetch); logged in but no list chosen yet (still mid-initial-setup) → back to `listSetupView`, since there's nothing else to show. `.home-link`'s CSS is a button reset (`background/border/padding/margin` cleared, `cursor: pointer`) layered under the same visual styling (`color: var(--link)`, no underline) it had as a link, matching the existing `.link-button` convention used by `login-info-btn`.

**Auth flow (OAuth2, standard redirect):**
1. `REDIRECT_URI` is computed once at load time as `window.location.origin + window.location.pathname` — it always points back at wherever the page is currently being served from, so no URL is hardcoded and the flow works unmodified on GitHub Pages, a custom domain, or `http://localhost` during local testing. This is also why a `file://` origin doesn't work: Mastodon requires a real, matching redirect URI.
2. User enters an instance domain. If no app credentials exist yet for that instance, `registerApp()` calls `POST /api/v1/apps` to dynamically register the app (with `REDIRECT_URI`) and stores `client_id`/`client_secret`; the instance name and a random `state` (from the local `randomUUID()` helper, not `crypto.randomUUID()` directly) are stashed in `localStorage` under `PENDING_INSTANCE_KEY`/`PENDING_STATE_KEY`, `state` is included in the authorize URL, and the whole page navigates to the instance's `/oauth/authorize` URL (`window.location.href =`, not a popup/new tab). `crypto.randomUUID()` requires a secure context (HTTPS, or `http://localhost`) and is `undefined` otherwise — this broke login with `crypto.randomUUID is not a function` when testing from a real phone over a plain `http://<lan-ip>:port` origin (works fine from `http://localhost`, per the testing instructions below, since that's still a secure context). `randomUUID()` calls `crypto.randomUUID()` when available and otherwise builds a v4 UUID by hand from `crypto.getRandomValues()`, which — unlike `randomUUID()` itself — has no secure-context restriction.
3. Mastodon redirects the browser back to `REDIRECT_URI` with `?code=...&state=...` (or `?error=...` if the user declines). On load, `init()` reads those query params, calls `completeAuthorization(code, returnedState)` — which requires `returnedState` to exactly match the stored `PENDING_STATE_KEY` (both pending keys are consumed/cleared regardless of outcome, so this check only ever accepts a code that was in flight from a login this same browser just started, closing a login-CSRF gap), then looks up the pending instance and its stored `client_id`/`client_secret`, exchanges the code via `exchangeCodeForToken()` (`POST /oauth/token`), and starts the session. The query string is stripped with `history.replaceState()` before any of this so the code/state aren't left in the URL/history.
4. Scope requested is `read write:favourites write:statuses` — enough for reading lists/timelines and for favouriting/reblogging, deliberately excluding general posting.

All credentials (`clientId`, `clientSecret`, `accessToken`, `listId`) are namespaced per-instance in `localStorage` via `storageKey(instance, name)` (`mastofoto:<instance>:<name>`), plus a `mastofoto:lastInstance` pointer used to auto-resume a session on load. Because there is no backend, the client secret is necessarily exposed in the browser — acceptable for this single-user use case but worth remembering if the scope of the app ever changes. Note that switching hosting origins (e.g. testing on `localhost` after having registered the app on the production URL) invalidates the cached `client_id`/`client_secret` for that instance, since Mastodon validates the redirect URI against what the app was registered with — clear that instance's localStorage entries (or log out) if authorization starts failing after a hosting change.

**Service worker:** `sw.js` (repo root, so its scope covers the whole app regardless of hosting path) caches the static shell only — `index.html`, `style.css`, `app.js`, `manifest.json`, the logo/favicon — never API responses (the fetch handler bails out on any cross-origin request, which covers every Mastodon API call automatically since those always hit `https://${instance}`). It's **network-first, cache-as-fallback**, not cache-first: every same-origin GET tries the network first and updates the cache on success, only falling back to the cache when the network fails. This was a deliberate choice given how often this project ships releases — a naive cache-first strategy would need its `CACHE_NAME` bumped in lockstep with every release (like `APP_VERSION`) to avoid serving a stale app indefinitely; network-first self-heals instead, so `CACHE_NAME` only needs bumping if the shell file list itself changes. Registered from `app.js` behind an `if ('serviceWorker' in navigator)` check, after `window.load`.

**Blurhash placeholders:** `decodeBlurhash()`/`blurhashToDataUrl()` in `app.js` are a from-scratch reimplementation of the public blurhash algorithm (https://blurha.sh) — deliberately not the npm package, to keep the app dependency-free. `buildMediaElement()` decodes each image's `att.blurhash` into a small (32×32) canvas, and sets the result as the `<img>`'s CSS `background-image` (cleared on `load`) so a blurred preview shows while the full-resolution file downloads. This needed `data:` added to the CSP's `img-src` (still no change to `script-src`/`style-src`, so it doesn't loosen anything script-execution-relevant). The `<img>` also gets `width`/`height` HTML attributes from `att.meta.original` (falling back to `att.meta.small`) — set from the image's own true dimensions, not a cropped/different ratio, so this only reserves layout space and lets the blurhash placeholder actually be visible before load; on a single-photo post nothing crops it further (see **Multi-photo grid** below for the one case that does). If the full-resolution file fails to load (dead URL, network error), the browser's own native broken-image icon — and, on some mobile browsers, a visible border/alt-text box — would otherwise appear on top of the blurhash background, since that background-image is a separate layer from the `<img>`'s own (failed) foreground content. `TRANSPARENT_PIXEL` (a 1×1 transparent PNG `data:` URI) is swapped into `img.src` on the `error` event specifically to prevent this: a tiny image that loads successfully replaces one that failed, so the element counts as "loaded" and the native broken-image chrome never renders, leaving the blurhash blur as the only visible result. This must **not** go through the same `load` listener that normally clears the blurhash background (that would defeat the point — the blur would vanish the instant the transparent placeholder itself finishes loading) — the blurhash's `load` listener is captured as a named `clearPlaceholder` function specifically so the `error` handler can `removeEventListener` it before swapping `src`, rather than being a throwaway arrow function as before. `alt` text is untouched by any of this and stays available to assistive technology regardless of whether the image data itself ever loaded. The same `TRANSPARENT_PIXEL` constant (plus a shared `setImgErrorFallback(img, fallbackSrc)` helper wrapping the identical `addEventListener('error', ..., { once: true })` pattern) is reused for custom emoji `<img class="emoji">`s — there's no blurhash to preserve there, so a failed emoji just quietly disappears instead of leaving an inline broken-image glyph in the middle of a sentence. Account avatars use the same helper with a different fallback, `AVATAR_FALLBACK` (`assets/favicon.png`), instead: a broken avatar shows the app's own icon rather than either the native broken-image icon or nothing. Because the post header (`header.innerHTML`, one avatar), the list-members preview (`item.innerHTML`, one avatar plus a possible emoji in the display name), and a status card's body (reblog banner, content-warning summary, and the post content itself — all independently `.innerHTML`-templated, each potentially containing emoji) build their markup as HTML strings rather than individual `createElement()` calls, the fallback can't be wired inline (a `<img onerror="...">` attribute would be blocked outright by this app's `script-src 'self'` CSP, which has no `'unsafe-inline'`) — instead each call site queries the already-inserted element(s) right after setting `innerHTML` and attaches the listener in JS. For a status card specifically, this is done **once**, in a single `card.querySelectorAll('img.emoji')` pass just before `renderStatusCard()` returns — after the header, banner, and body have all already been appended to `card` — rather than repeating the same query separately after each of those three `.innerHTML` assignments.

**Multi-photo grid:** a post with more than one photo gets different treatment than a single-photo post. `buildMediaElement()` already builds a `photos` array (images only, since Mastodon's own server-side validation never lets a status mix image attachments with a video/gifv/audio attachment — a status is either 1-4 images, or exactly one video/gifv/audio, so `photos.length` is always an accurate, unambiguous count to key off of). When `photos.length > 1`, the `.status-media` container gets an extra `status-media-grid` class and a `--media-columns` custom property, set from `mediaGridColumns(photos.length)` (`pure.mjs`, DOM-free and covered by `pure.test.mjs`): 3 columns when the count divides evenly by 3, otherwise 2 — a plausible default, not an attempt at perfectly equal rows for every count (5 photos, for instance, still ends up with a shorter last row, which is accepted rather than special-cased). `.status-media-grid img, .status-media-grid video` then get `aspect-ratio: 4 / 3` + `object-fit: cover` in `style.css`, forcing every tile to the same crop instead of its natural aspect ratio. Because `grid-template-columns: repeat(var(--media-columns, 2), minmax(0, 1fr))` uses equal-width tracks across the *whole* grid (not per-row), every tile — including a lone item in a shorter last row — gets the same column width and therefore, with the aspect ratio fixed, the same height too; no extra "make the last item span full width" rule is needed. The `minmax(0, 1fr)` (rather than a bare `1fr`, which resolves to `minmax(auto, 1fr)`) is required, not cosmetic: a grid track's `auto` minimum falls back to its content's intrinsic size, and a raw photo `<img>` carries `width`/`height` HTML attributes reflecting its full resolution (see above) — often thousands of pixels — so without the explicit `0` floor the grid would size its columns to the photo's real dimensions and overflow the card sideways on mobile, exactly like the pre-existing single-column rule already avoids via its own explicit `minmax(140px, 1fr)`. A single-photo post never gets `status-media-grid` and keeps rendering exactly as before: full aspect ratio, uncropped.

**Logo & favicon assets:** `assets/logo.png` is a pre-rendered transparent PNG of the word "Mastofoto" set in the Google Font "Pacifico" — it exists specifically so the page never has to load a webfont at runtime. `assets/favicon.png`/`assets/favicon.ico` are the same treatment applied to just the letter "M", cropped/centered to fill the icon square. Both were generated with Pillow (`ImageFont.truetype` + `ImageDraw.text`, measuring the glyph's `textbbox` to scale and center it before rendering) from the actual Pacifico TTF (fetched from `fonts.gstatic.com`), not with a browser. To regenerate either (e.g. a different color/size), re-run that kind of script rather than trying to reintroduce a `<link>` to Google Fonts. `assets/favicon.png` itself stays transparent and is used only for the browser-tab `<link rel="icon">`s — a transparent icon reads fine at that tiny size against a browser's own tab chrome. The mobile/PWA home-screen icon is a separate asset, `assets/app-icon.png` (referenced by the `apple-touch-icon` `<link>` and by `manifest.json`'s single 512×512 `icons` entry), because a transparent icon looks inconsistent once a phone's launcher composites it over an arbitrary wallpaper — it needs an opaque background baked in. `app-icon.png` is generated by alpha-compositing the unmodified `favicon.png` (same blue "M", same color, untouched) over a diagonal linear gradient from `#232a32` (top-left) to `#12151a` (bottom-right) — dark tones centered on the app's own dark-theme background `#191d20`, chosen so the brand blue "M" (`#2b90d9`) keeps ≥4.2:1 contrast against every point of the gradient (computed with the WCAG relative-luminance formula, the same method used for the theme's other contrast checks) while still reading as a deliberate, on-brand "glossy dark" icon rather than a flat fill. If the icon ever needs regenerating, reproduce that same composite (transparent `favicon.png` over the gradient) rather than re-drawing the letter from scratch, and re-check contrast if the gradient colors change.

**Header action "buttons" styled as links:** `#session-info`'s "Settings"/"Log out" and the info button are deliberately still `<button>` elements, not `<a>` — they trigger an in-page view switch or clear session state, they don't navigate to a URL, and a real `<button>` is keyboard-operable (Enter/Space, tab order) for free. Only the CSS changed: no background/border, text colored with `--link`, underline appears on `:hover`. Don't add `opacity` to dim them at rest like the old filled-button style did — that was tried and reverted because diluting `--link` with opacity dropped it back under the 4.5:1 contrast minimum in light mode; if a "muted until hover" look is wanted again, pick a distinct, separately-contrast-checked color for the resting state instead of fading the existing one.

**Icons:** every icon in the app (the header's Settings/Info/Log out, and the feed's Favourite/Reblog/View post buttons plus the "boosted" banner) is a small inline `<svg>` (in a `<span class="btn-icon" aria-hidden="true">` wrapper, `.btn-icon svg` fixed at 16px, `.btn-icon svg { display: block; width/height }` in `style.css`) rather than an emoji or an external image file. All of them use `stroke="currentColor"` (with a couple of small `fill="currentColor"` accents, e.g. the Settings icon's dots) instead of a fixed color, specifically so they inherit whatever CSS `color` the surrounding button/text already has — the header's `--link-header`/`--link` on hover, or the feed buttons' `--text` at rest and `--accent-contrast` when `.active` (favourited/reblogged) — and so both light and dark theme are covered automatically with one asset instead of two. Being inline markup rather than `<img src="icon.svg">` files, they add effectively no page weight and can react to CSS in a way an external SVG file referenced by `<img>` cannot. The feed action buttons keep their visible count in a separate `<span class="btn-count">`, updated on click by `toggleFavourite()`/`toggleReblog()` via `btn.querySelector('.btn-count').textContent = ...` — don't go back to overwriting the whole button's `textContent`, since that would destroy the icon `<span>` along with the count. `.status-actions .btn-icon`/`.reblog-banner .btn-icon` override the header's `.btn-icon { opacity: 0.7 }` back to full opacity, since that dimming was chosen for the header's plain-link look and isn't appropriate on the feed's solid-background buttons. The now-unused `.icon-btn` CSS rules (from an earlier, pre-SVG version of the header buttons) were removed — don't reintroduce them. The login page's `.feature-checklist` reuses this same inline-SVG-with-`currentColor` pattern for its three checkmark bullets, tinted via `.check-icon { color: var(--link); }` rather than a new color token — it's a decorative accent at icon size, not body text, so it doesn't need its own contrast-checked token the way `--link`/`--btn-primary-bg` do for actual text/button-fill use.

**Theme (light/dark):** every color in `style.css` is a CSS custom property, defined on `:root` (light, the default) and re-declared under `:root[data-theme="dark"]` — no bare hex/rgba should appear outside those two blocks; a new color needs a token added to both, even if the value is identical in both themes (e.g. `--btn-primary-bg`, `--accent-contrast`, `--overlay-bg` don't change between themes, but stay tokenized for consistency and so every color has exactly one place to look it up). The background asked for specifically was `#191d20`. `--shadow` is the one value that *does* differ non-trivially — `.card`/`.status-card`'s box-shadow is bumped to a higher opacity in dark mode since a shadow the same strength as light mode barely reads against a dark page. `app.js` computes the effective theme once at startup (`getPreferredTheme()`): an explicit choice in `localStorage` (`mastofoto:theme`) wins, otherwise it falls back to `prefers-color-scheme`. `applyTheme()` sets the `data-theme` attribute on `<html>` and also updates the `<meta name="theme-color">` tag so the mobile/PWA chrome matches. The picker lives in Settings (`#theme-select`) as a plain `<select>`, seeded with the effective theme on load and persisting explicitly on `change` — there's no "system/auto" option once a user has picked one, and no listener for the OS preference changing while the app is open (out of scope; re-opening the app or re-toggling covers it). The login page's `.login-form` panel (framing the instance-domain field and Connect button) reuses `var(--bg)` — the page background token, not `--surface` — as its own background specifically because it sits inside a `.card`, which is already `--surface`; since `--bg` and `--surface` deliberately invert their relative lightness between themes (light mode: `--surface` `#fff` lighter than `--bg` `#f2f3f5`; dark mode: `--surface` `#22262b` lighter than `--bg` `#191d20`), reusing `--bg` here reads as a subtly recessed inset box in both themes without needing a third, dedicated token.

**Post text size:** a second Settings control, right below the theme picker, lets the user scale post body text independently of the theme — `#font-size-slider`, a native `<input type="range" min="-0.5" max="0.5" step="0.1">` representing an *offset* in `rem` from the default `1rem`, not an absolute size. `getPreferredFontSizeOffset()`/`applyFontSizeOffset()` mirror the theme functions exactly (localStorage key `mastofoto:postFontSizeOffset`, applied once at startup before login), except the value is written to a single CSS custom property (`--post-font-size`, consumed by `.status-content { font-size: var(--post-font-size, 1rem) }` and the Settings-page live preview `.font-size-preview`) rather than an attribute, since a numeric range has no `data-*`-friendly discrete states the way light/dark does. The slider fires on `input`, not `change`, so both the persisted value and the live preview update continuously while dragging rather than only on release. Tick marks are a hand-drawn overlay (`.font-size-slider-wrap > .font-size-ticks`, 11 `<span class="tick">`s laid out with `justify-content: space-between`, one per 0.1 step, the center one distinguished as `.tick-default`) rather than a `<datalist>` — a first attempt used `<datalist>`, but its native tick rendering is too subtle to notice in Chrome/Firefox/Edge and doesn't render at all in Safari; a manually drawn row underneath the track (inset 8px each side to roughly match the thumb's own travel inset) looks identical and equally visible in every browser. It's `aria-hidden="true"` and `pointer-events: none` since it's a purely visual ruler — the slider's own native `step` is what actually makes the thumb snap, independent of any visual tick. Deliberately **no numeric readout** next to the slider, since the ticks plus the live preview text were judged sufficient feedback and a number was considered visual clutter for an 11-step range centered on an obvious, distinctly-colored middle tick. The preview text (`.font-size-preview`) is `aria-hidden="true"`: it's a sighted-only convenience, since a screen reader user already gets the current value announced by the native range input itself and doesn't need a redundant sample sentence read aloud. `Math.round(value * 10) / 10` guards against binary floating-point drift (e.g. `0.30000000000000004`) before the offset is persisted or applied.

**Brand blue vs. accessible blue:** `#2b90d9` (the literal brand color baked into `assets/logo.png`/`assets/favicon.png` and `manifest.json`'s `theme-color`) measures only ~3.45:1 against white, short of the 4.5:1 normal-text requirement — so it is used **only** for those non-text, decorative contexts and is deliberately **not** a CSS variable in `style.css`. Every place that needs actual contrast uses one of two separate, accessible tokens instead: `--btn-primary-bg` (`#1c69a0`, identical in both themes — button-fill contrast against its own white label doesn't depend on the page theme, since the button *is* the immediate background) for solid buttons/`.new-badge`/the active favourite-reblog state, and `--link` (`#1a6699` light / `#5aa9e6` dark — a link's background *is* the page surface, which does change per theme, so this one can't share a single value like `--btn-primary-bg` does) for inline text links and the photo focus-visible outline. Don't reintroduce `#2b90d9` (or a `var(--accent)`-style alias for it) into any text- or button-fill rule — that's exactly the contrast failure this split fixed.

**Accessibility:** contrast has been checked by computing actual WCAG ratios (not eyeballed) for every token pair — `--text-tertiary`, `--border-strong`, `--btn-primary-bg`, and `--link` were all measured failures in the original palette (before the brand/link split above) and are now tuned to pass (≥4.5:1 for text, ≥3:1 for UI component borders) in both themes; re-verify with the relative-luminance formula (not intuition) if any of these tokens change again. The page has exactly one `<h1>` (`.sr-only`, "Mastofoto", in the header, present across all views since the header itself never hides) with each view's own heading correctly nested under it as `<h2>`/`<h3>`/`<h4>` — don't add a second `<h1>` if a view's title ever needs promoting for some other reason.

**Responsive layout:** all mobile overrides live in a single `@media (max-width: 480px)` block at the very end of `style.css`, rather than scattered near each base rule — this matters because a media query has the same specificity as the plain selector it targets, so with equal specificity the rule *later in the file* wins regardless of the media query; keeping the block at the end guarantees every override comes after its unconditional base rule. Notable overrides: `#session-info`'s "Settings"/"Log out" buttons wrap their label in `<span class="btn-icon">`/`<span class="btn-label">`, and the mobile rule hides `.btn-label`, leaving just the icon (sized up via `#session-info .btn-icon svg { width/height: 20px }`, since the icons are fixed-size inline SVG rather than a font glyph `font-size` could scale) in the same tap-target area used at desktop width; `.status-author .username` gets a fixed `width: 195px` with `overflow: hidden` and a right-edge `mask-image` fade (`-webkit-mask-image` too, for Safari) instead of the shared `text-overflow: ellipsis` — chosen specifically so its width never depends on how much room the corner-pinned date needs on the same row, which a flex-shrinking width would (see **New-post highlighting** below for why that row no longer wraps on mobile at all). Don't reintroduce a second `@media (max-width: 480px)` block elsewhere in the file — add new mobile rules to the existing one at the bottom. The login page's `.login-columns` wraps the feature checklist and `.login-form` in a `display: flex` row so the two sit side by side above the mobile breakpoint (`flex: 1; min-width: 0` on both children, the same overflow-safe pattern as `.member-info`/the multi-photo grid) — the mobile override switches it to `flex-direction: column` and moves the two children's bottom margins back onto themselves (removed at the row level, where side-by-side siblings don't need one) to restore the original stacked spacing.

**Timeline configuration:** the app intentionally supports exactly one active timeline at a time (not a multi-list browser) — but that one timeline can be either a Mastodon list or the account's Home timeline. `showListSetup()` always prepends a `<option value="home">Home timeline</option>` to `#list-select` (`HOME_TIMELINE_ID = 'home'`, a sentinel string that can never collide with a real numeric list id) before fetching `/api/v1/lists` and appending one option per list; the choice is persisted as `listId` per-instance (so the sentinel string `'home'` is what ends up stored when that's picked) and reused on future logins — `startSession()`/`el.changeListBtn`'s handler treat it exactly like a real list id, since nothing about resuming a saved choice needs to know which kind it is. Home timeline requires no extra OAuth scope beyond the `read` already requested. The "Settings" button (`change-list-btn` — the id is unchanged from before the rename, still just opens `#list-setup-view`) re-opens the same screen to switch later; that screen also holds the theme picker (see **Theme** below), unrelated to any single Mastodon list/instance. When a real list is selected, that screen previews its membership via `loadListMembers()` (`GET /api/v1/lists/:id/accounts?limit=80` — a single page, no pagination, since these are meant to be small curated lists), sorted alphabetically by `display_name || username` with `localeCompare(..., { sensitivity: 'base' })`; `updateListPreview(listId)` is the single gatekeeper for this — it calls `loadListMembers()` for a real list id, or just clears/hides the members list when `listId` is falsy or the home sentinel, since "membership" isn't a concept the Home timeline has. It runs on the select's `change` event and once right after the dropdown is first populated in `showListSetup()`. The list has no `max-height`/scroll of its own — it renders in full and lets the page scroll. Each member's name is linked to `account.url` (profile), same `isHttpUrl()`-guarded fallback-to-plain-text pattern as the post author links; the name and `@handle` are wrapped together in a `.member-info` element so their relative layout can change per breakpoint without touching the surrounding `<li>` — on desktop it's a flex row (name and handle side by side, as before), but on mobile the fixed `@media (max-width: 480px)` block switches it to a column (handle below the name) since a long display name plus a long handle on one line could overflow the row on a narrow screen; both `.member-name` and `.member-handle` also get `overflow-wrap: anywhere` so a single very long unbroken name or handle can't do the same on its own. If a Mastodon account has no lists at all, `#no-list-message` still only hints that lists are optional (rather than blocking setup) since Home timeline is always a usable option regardless.

**Timeline & photo filtering:** `runLoadTimeline()` fetches `/api/v1/timelines/home` when `state.currentListId === HOME_TIMELINE_ID`, otherwise `/api/v1/timelines/list/:id`; either way it paginates using the `Link: rel="next"` header (falling back to the last returned status id via `parseNextMaxId()`), and then filters results client-side with `hasPhoto()` — only statuses (or reblogs) with at least one `media_attachments` entry of type `image` are rendered. This filtering happens after pagination, so a single fetched page can yield zero photo posts — more likely on Home timeline than on a small curated list, simply because it mixes in every followed account's non-photo posts too. There is no "Load more" button; scrolling near the bottom (or a short list already fitting on screen) triggers `maybeLoadMore()`, which keeps calling `loadTimeline(true)` on its own — via mutual recursion, not a tight loop, so the tab stays responsive — until a page actually yields a photo or `state.hasMore` goes false, capped by `MAX_CONSECUTIVE_EMPTY_PAGES` (20) as a backstop against a pagination bug or a pathologically photo-sparse timeline turning into an unbounded chain of requests. See **Lazy loading** below for the full mechanism, including why this isn't just `loadTimeline(true)` called straight from an `IntersectionObserver` callback.

**Lazy loading:** `loadTimeline()` is called from three independent places — a fresh list selection, pull-to-refresh, and auto-continuation while scrolling — so a plain boolean "busy" flag would let one caller silently no-op if it overlapped another (concretely: pull-to-refresh showing "Refreshing…" and resetting the label without an actual refresh happening, if a background auto-load load happened to be in flight at that exact moment). Instead every call goes through a shared promise queue (`timelineQueue`, plus a `pendingTimelineCalls` *counter* — not a boolean, since two overlapping calls settling out of order would otherwise flip a shared boolean back to "idle" while one is still queued): a call is never dropped, it just waits its turn and then genuinely runs. `loadTimeline()` is a thin wrapper around `runLoadTimeline()` (the actual fetch, returning `true`/`false` for success) that manages this queue and, after every settled call, invokes `maybeLoadMore()` — this single function is what re-triggers auto-paging through a run of zero-photo pages (the sentinel doesn't move, so a passive `IntersectionObserver` alone would never refire) and what auto-fills a short list right after a fresh load (also no enter/exit transition for the observer to catch). `maybeLoadMore()` re-derives "is the sentinel close enough to load more" itself via a live `getBoundingClientRect()` check (`sentinelNearViewport()`) rather than trusting the observer's own (batched/throttled) entry — the `IntersectionObserver` watching `#scroll-sentinel` (`rootMargin` sharing the same `AUTO_LOAD_MARGIN_PX` constant used by that check, so the two distances never drift apart) exists only as a cheap "something changed, go re-check" wakeup, since that's far less costly than a manually-throttled raw `scroll` listener. `maybeLoadMore()` checks `el.timelineView`'s hidden state *before* the geometry check — a hidden ancestor collapses `#scroll-sentinel`'s rect to all zeroes, which would otherwise misread as "at the very top of the screen" and fire a fetch before a session even exists (the observer's `observe()` call happens at module-eval time, before login). On a fetch error the chain simply stops (no retry loop, matching that an `IntersectionObserver` wouldn't retry on its own anyway) — the existing `#timeline-error` banner shows via the unchanged `showError()`, and recovery is via pull-to-refresh or scrolling away and back.

**New-post highlighting:** on every non-append `loadTimeline()` call (i.e. a fresh list load, not an auto-continuation), `state.lastSeenBefore` is set from the previous value of a per-list `localStorage` marker (`lastSeenKey(listId)` → `lastSeen:<listId>`), *before* that marker is overwritten with the newest fetched photo status's `created_at`. `renderStatusCard()` then flags a card `is-new` (only used for the `"New"` badge shown next to the timestamp — the card itself is no longer tinted). `.new-badge` and `.status-date` are no longer wrapped in a `.status-meta` container, and — unlike the date — the badge isn't even a descendant of `.status-header` any more. `renderStatusCard()` appends `.new-badge` as the very first child of `.status-card` itself, before the reblog banner or the header, specifically so it anchors to `.status-card` (`position: relative`) rather than `.status-header`: `top: 16px; right: 16px`, matching the card's own padding, so it sits in the exact same spot for every post regardless of whether a `.reblog-banner` pushes the header down underneath it — a reblog and a plain post both get the badge in the identical corner. `.status-date`, by contrast, stays inside `.status-header` (`position: relative`, a fixed ~48px tall row since `.status-author`'s two lines never wrap) and anchors to *that* instead, at `bottom: 0; right: 0` — lining up with the username row below it, wherever the header happens to sit. Anchoring the date to `.status-header` rather than `.status-card` matters — the header's height is stable regardless of post body length, while the card's isn't, so `bottom: 0` on the date would be meaningless anchored to the card. This whole scheme replaced an earlier design where the badge/date were real flex children stacked together in a `.status-meta` column (working, but needing a different empirically-tuned `margin-top` per breakpoint to fake the date's alignment with the username row whenever the badge wasn't present — fragile, since any font-size/line-height change nearby could silently throw it off — and, since badge and date shared one flex parent, unable to give the badge a card-relative fixed point independent of the header's own position). Because both are taken out of flow entirely, `.status-author` (the only remaining flex sibling besides the avatar) would otherwise expand to the full row width and run its truncated text underneath them — so `.status-header` carries a permanent `padding-right` (110px desktop, 90px mobile) sized to fit the corner column, unconditionally rather than only when `is-new` like before, since the date is now always present as an overlay. When the *top-level* `status.created_at` — not `original.created_at`, since for a reblog the top-level date is when it entered the timeline, which is what "new" should track — is newer than `state.lastSeenBefore`. On a list's very first-ever view there is no stored marker, so nothing is flagged as new (avoids highlighting the whole history). The marker only advances on a fresh load, so posts stay marked "new" for the rest of that same viewing session even as lazy-loading fetches older pages.

**Rendering & sanitization:** `renderStatusCard()` builds each post's DOM manually (no templating library). Media (`buildMediaElement()`) uses `media_attachments[].url` (the full-resolution file) rather than `preview_url` (a thumbnail Mastodon caps around ~400px on the long edge) — given the app's whole purpose is showing photos, the preview would be a visible quality regression; `preview_url` is kept only as a fallback if `url` is ever missing, and images are marked `loading="lazy"` since full-resolution files are heavier. It is always rendered before the body text — including inside content-warning posts, where both live inside the `<details>` collapse. Images/videos are shown at their original aspect ratio (`height: auto`, no cropping). Status `content` from the API is HTML and is passed through `sanitizeStatusHtml()`, a hand-rolled allowlist sanitizer (permitted tags in `ALLOWED_TAGS`; all attributes stripped except a safety-checked `href` on `<a>`, which also gets `rel`/`target` forced) rather than trusting Mastodon's server-side sanitization outright. `href` values are validated with `isHttpUrl()` (imported from `pure.mjs`) — an allowlist requiring the resolved URL's scheme to be `http:`/`https:` — rather than a denylist of known-bad schemes like `javascript:`. `isHttpUrl()`'s second parameter (`base`) defaults to `window.location.href` in the browser and to `undefined` in Node (detected via `typeof window`), so every existing call site in `app.js` behaves exactly as before without passing it explicitly, while `pure.test.mjs` can still call it with plain absolute URLs. Before attributes are stripped, the sanitizer detects Mastodon's hashtag markup (`class="...hashtag..."` or `rel="tag"`) and re-tags the link with a `tag-link` class so hashtags can be styled smaller/muted in CSS separately from regular links. The `isHttpUrl()` guard is also reused outside the sanitizer, for two links that both only render when the relevant field is present and passes the check (falling back to plain, non-linked text/no button otherwise): the author's `username` element as an `<a href="original.account.url">` (the author's **profile**, not the post — don't confuse the two `url` fields, `account.url` vs the status's own `url`), and a "View post" link/button (`.view-original-btn`) in `.status-actions`, using `original.url` (the status's own permalink, on its origin instance), placed after the favourite/reblog buttons.

**Custom emoji shortcodes:** Mastodon never resolves a `:shortcode:` itself — `content`, `spoiler_text`, and `display_name` all carry the literal shortcode text, alongside a separate `emojis` array (on the Status for the first two, on the Account for the third) mapping each shortcode to an image `url`. `renderEmojiText(text, emojis)` (in `pure.mjs`, DOM-free and covered by `pure.test.mjs`) handles the plain-text cases — `display_name` (status header, reblog banner, list-members preview) and `spoiler_text` — by escaping the text first and then replacing each shortcode still present in the *escaped* string with an `<img class="emoji">`, guarded by the same `isHttpUrl()` allowlist as every other external URL in the app; a shortcode with no matching (or unsafe) emoji entry is left as plain escaped text. `content` is HTML, not plain text, so it can't go through `renderEmojiText()` directly — instead `sanitizeStatusHtml()` takes an `emojis` param and calls `renderEmojiText()` per *text node* during its existing DOM walk (`replaceEmojiShortcodes()`), replacing a matching text node with the parsed result's child nodes via `textNode.replaceWith(...)`. This runs after the tag/attribute allowlist check for that DOM level, so the `<img>` tags it introduces are never subject to (or stripped by) `ALLOWED_TAGS`, which deliberately doesn't include `IMG` — a raw `<img>` tag actually present in a status's `content` is still stripped like any other disallowed tag, only ones `renderEmojiText()` itself constructs from a validated emoji URL survive. `img.emoji` is styled at a fixed `1.2em` square so it renders inline at roughly text size regardless of the source image's actual dimensions. `escapeHtml()` itself also moved into `pure.mjs` (both to build `renderEmojiText()` on it and to let `pure.test.mjs` cover it directly); `app.js` keeps a local `escapeAttr` as an alias, unchanged at every call site.

**Security headers:** since GitHub Pages serves this app with no custom HTTP headers, `index.html` sets a `Content-Security-Policy` via `<meta http-equiv>` (`script-src 'self'`, `object-src 'none'`, `form-action 'none'`, etc.) as defense-in-depth. Note `<meta>` CSP cannot carry a `frame-ancestors` directive (browsers ignore it there), so this does not protect against clickjacking — that would require a real HTTP header from something fronting GitHub Pages.

**Pull to refresh:** `#pull-refresh` is a normally-zero-height flow element (not `position:fixed`) sitting right above `#timeline-container`; growing its inline `style.height` on `touchmove` naturally pushes the feed down, mimicking native pull-to-refresh. It only arms when `el.timelineView` is visible and `window.scrollY === 0` at `touchstart` (so it never fires mid-scroll or from other views), and calls `preventDefault()` on `touchmove` (registered `{ passive: false }`) to stop the browser's own rubber-banding while dragging — `body` also sets `overscroll-behavior-y: contain` so the native overscroll/refresh gesture doesn't fight with this one. Crossing `PULL_THRESHOLD` (70px, from a raw drag distance damped by ×0.5, capped at `PULL_MAX`) flips the `.ready` class (rotates the arrow, swaps the label) and, on release past that threshold, calls the same `loadTimeline(false)` used by a fresh list load — this exists specifically because standalone/home-screen mode on iOS and Android has no built-in reload gesture the way a regular browser tab does. `touchstart`'s arming check no longer guards on a "busy" flag — since `loadTimeline()` calls now go through the shared queue described in **Lazy loading** above, correctness doesn't depend on blocking the gesture from starting; `await loadTimeline(false)` here simply stays pending for as long as it actually takes (including any wait behind an unrelated auto-load already in flight), so "Refreshing…" is only ever shown for a genuinely in-progress refresh, never a false-positive flash.

**Lightbox:** clicking (or, since the feed's `<img>`s are `tabindex="0" role="button"`, focusing + pressing Enter/Space on) a photo (`buildMediaElement()`'s `img` elements only, not video/gifv) calls `openLightbox(photos, index, triggerEl)`, where `photos` is that post's *own* image attachments only (built once per `buildMediaElement()` call, filtered from `media_attachments` before the per-attachment loop, mapped to `{ src, alt }`) and `index` is that photo's position within it — not a single `(src, alt)` pair, specifically so the lightbox knows what else is in the same post's gallery. It reuses the same full-resolution URLs already used in the feed and just displays the current one larger in a single fixed-position `#lightbox` overlay (`role="dialog" aria-modal="true"` in `index.html`, shown/hidden via the shared `.hidden` class). There's exactly one lightbox `<img>` in the DOM, repointed via `showLightboxPhoto(index)` on open and on every navigation — not one per photo. On a post with more than one photo, the lightbox can move between them: `ArrowLeft`/`ArrowRight` (guarded to only act while the lightbox is actually open, unlike `Escape` which is harmless to call unconditionally), and a horizontal touch swipe past `LIGHTBOX_SWIPE_THRESHOLD` (50px) — `touchmove` only calls `preventDefault()` once the drag is clearly more horizontal than vertical, so a vertical swipe/scroll isn't hijacked, and `touchend` also calls it when a swipe was actually acted on, which suppresses the synthetic `click` event that would otherwise immediately close the lightbox right after swiping. Both directions clamp at the gallery's ends rather than wrapping around. Opening moves focus to `#lightbox-close` (a visible × button); closing — via that button, a click anywhere on the overlay including the image, or Escape (all wired once at startup rather than per-photo) — returns focus to whichever photo triggered it (`lightboxTrigger`, captured at open time).

**Favourite/reblog:** `toggleFavourite()`/`toggleReblog()` call the respective `/favourite`/`unfavourite` and `/reblog`/`unreblog` endpoints and update the button label/state from the API response rather than optimistically.
